데이터 모델링의 이해

현실의 업무를 데이터베이스로 옮기는 첫 단계입니다. 이 파트의 핵심은 용어 구분 — 데이터 모델·엔터티·속성·관계·식별자의 뜻을 분명히 잡는 것입니다.

1. 데이터 모델의 이해

정의

데이터 모델이란 현실 세계의 복잡한 정보를 컴퓨터에 저장하기 위해 그린 설계 도면이다.

ex) 회원·상품·주문 같은 정보를 어떻게 저장하고 연결할지 데이터베이스 구조로 시각화하는 과정.
💡 쉽게 말하면

데이터 모델링은 현실을 지도로 그리는 일이에요. 실제 도시엔 건물·사람·차가 가득하지만 지도엔 길과 주요 건물만 간단히 그리죠. 똑같이, 복잡한 회사 업무에서 "저장·관리할 정보"만 골라 깔끔한 그림으로 옮기는 게 데이터 모델링입니다.

데이터 모델링의 단계 — 개념 → 논리 → 물리 ('개-논-물')

추상적인 개념에서 구체적인 구현 단계로 진행됩니다. 각 단계의 산출물이 자주 출제됩니다.

1

개념적 데이터 모델링 (Conceptual)

데이터 요구사항을 분석해 핵심 엔터티와 그 관계를 나타내는 ERD를 생성. 전사적 관점, 추상화 수준이 가장 높음.

2

논리적 데이터 모델링 (Logical)

속성·PK·FK를 채우고 정규화 수행. DBMS와 무관. 모델링의 최종 완료 상태.

3

물리적 데이터 모델링 (Physical)

실제 DBMS에 맞춰 CREATE TABLE + 인덱스·파티션·자료형 명시. 성능·보안·가용성 고려.

4

데이터베이스 운영

테이블에 데이터가 차곡차곡 쌓인 상태. 사용자가 SQL로 조회·입력·수정.

🏠 집 짓기로 비유

개념적 = '방3·거실1' 손스케치 → 논리적 = 치수·배관까지 그린 설계도면 → 물리적 = 벽돌로 실제 시공. 뒤로 갈수록 구체적·기술적이 됩니다.

단계결과물비유
1. 개념적 모델링핵심 엔터티·관계 ERD (큰 그림)손으로 그린 스케치
2. 논리적 모델링속성·키 상세 ERD + 정규화정식 건축 도면
3. 물리적 모델링DBMS별 CREATE TABLE + 인덱스·파티션시공 계획서
→ 운영데이터가 쌓인 실제 데이터베이스입주 완료된 건물

SQL 실전 — 모델이 곧 테이블이 된다

논리 모델의 PK는 물리 모델에서 PRIMARY KEY 제약(식별자)이 됩니다.

-- 논리 모델의 '회원/상품/주문' 엔터티 → 물리 모델의 테이블 CREATE TABLE MEMBER ( MEMBER_ID VARCHAR2(10) PRIMARY KEY, -- 식별자 NAME VARCHAR2(50) NOT NULL, PHONE VARCHAR2(20) ); CREATE TABLE ORDERS ( ORDER_ID NUMBER PRIMARY KEY, MEMBER_ID VARCHAR2(10) REFERENCES MEMBER(MEMBER_ID), -- 관계=FK ORD_DATE DATE DEFAULT SYSDATE ); CREATE INDEX IDX_ORDERS_MEMBER ON ORDERS(MEMBER_ID); -- 성능용 인덱스(물리)

2. ERD 작성 절차 보충

ERD는 엔터티와 관계를 그리는 표준 방법(1976년 피터 첸 고안). 작성은 6단계 순서로 진행되며 이 순서가 자주 출제됩니다.

1

엔터티를 도출하고 그린다

업무에서 관리할 집합(덩어리)을 찾습니다.

2

엔터티를 배치한다

중요한 엔터티를 왼쪽 상단에 배치합니다.

3

엔터티 간 관계를 설정한다

연결되는 엔터티끼리 선을 긋습니다.

4

관계명을 서술한다

어떤 행위/존재가 있는지 이름을 붙입니다.

5

관계 참여도를 표현한다

서로 몇 개씩 참여하는지(예: 고객1 : 계좌N).

6

관계의 필수 여부를 표현한다

반드시 있어야 하는 관계인지 표시합니다.

★

암기팁  "누가 있나(1·2) → 어떻게 잇나(3) → 이름(4) → 몇 개(5) → 필수(6)". 관계 3종(관계명→참여도→필수)은 항상 뒤쪽에 옵니다.

❓ 확인 퀴즈 · ERD 절차
ERD 작성 절차로 올바른 것은? (ㄱ엔터티도출 · ㄴ배치 · ㄷ관계설정 · ㄹ관계명 · ㅁ참여도 · ㅂ필수여부)
정답 ① 도출→배치→관계설정→관계명→참여도→필수여부.

3. 엔터티 (Entity)

정의

엔터티란 업무에서 관리해야 할 정보의 덩어리(명사)다. 실제 테이블의 후보가 된다.

ex) 쇼핑몰이라면 회원·상품·주문·배송 같은 명사 하나하나가 엔터티. 각 엔터티의 개별 사례('김철수 회원')를 인스턴스(한 행)라 한다.
📦 쉽게 말하면

엔터티는 엑셀 시트 한 장의 제목('회원' 시트, '주문' 시트)이에요. 표 자체가 엔터티(MEMBER), 헤더가 속성, 각 행이 인스턴스입니다.

엔터티의 5가지 특징 — '업·식·인·속·관'

업 — 업무에 필요
관리할 가치가 있는 정보여야 한다.
식 — 식별 가능
식별자로 유일하게 구분된다.
인 — 인스턴스 ≥ 2
2개 이상의 행이 존재해야 한다.
속 — 속성 ≥ 2
2개 이상의 속성을 가진다.
관 — 관계 보유
다른 엔터티와 최소 1개 이상의 관계를 가진다.

SQL 실전 — 엔터티는 테이블이 된다

CREATE TABLE MEMBER ( MEMBER_ID VARCHAR2(10) PRIMARY KEY, -- 식별자 NAME VARCHAR2(50), PHONE VARCHAR2(20), JOIN_DATE DATE ); -- 인스턴스(행) 입력 INSERT INTO MEMBER VALUES('M01', '김철수', '010-1111', DATE '2026-01-15'); INSERT INTO MEMBER VALUES('M02', '이영희', '010-2222', DATE '2026-02-08'); -- 조회: 두 인스턴스에서 두 속성만 골라 보여준다 SELECT MEMBER_ID, NAME FROM MEMBER;

4. 속성 (Attribute)

정의

속성이란 엔터티가 가지는 세부 정보 항목, 곧 컬럼이다. 엔터티를 설명하는 가장 작은 단위다.

ex) 명함 한 장에서 명함 자체는 엔터티(사람), 이름·전화번호·이메일 같은 각 항목이 속성. 이름은 더 이상 쪼개지지 않는 최소 단위.
🔎 엔터티 / 인스턴스 / 속성 / 속성값

회원 테이블에서 각 행 = 인스턴스, 각 컬럼 = 속성, 각 칸 = 속성값(Value). 예: (M01, 김철수, 010-1111)에서 '010-1111'이 속성값.

속성의 3가지 분류 기준

① 특성

기본 / 설계 / 파생

데이터가 어디서 왔는가

② 분해

단순(원자) / 복합

더 쪼갤 수 있는가

③ 값 개수

단일값 / 다중값

한 인스턴스에 몇 개?

기준종류의미 (예)
① 특성기본 속성업무에서 직접 추출된 본래 속성 (이름, 전화번호, 주소)
설계 속성설계 과정에서 새로 만든 속성 (회원ID, 상품코드)
파생 속성다른 속성에서 계산되어 나온 속성 (총주문금액 = 수량 × 단가)
② 분해단순(원자) 속성더 이상 분해 불가 (이름, 나이)
복합 속성여러 의미가 합쳐진 형태 — 분해 저장 시 활용도↑ (주소 = 시+구+동)
③ 값 개수단일값 속성하나만 가짐 (주민번호)
다중값 속성여러 개 가능 → 별도 엔터티로 분리 (전화번호: 집·휴대폰)
★

시험 단골  "주민번호로부터 구한 나이"는 파생 속성. 복합 속성(1-1-4)과 복합식별자(1-1-6)는 다른 개념 — 복합 속성은 한 속성을 여러 의미로 쪼갬, 복합식별자는 여러 속성을 묶어 PK로 씀.

구성에 따른 분류 & 명명 규칙

속성은 역할에 따라 PK 속성·FK 속성·일반 속성으로도 나뉩니다.

  • 코드가 아닌 현업 용어로 명명 ('회원_등록일' O, 'regdt' X).
  • 명사형으로 ('주문수량' O, '주문은얼마인가' 서술식 X).
  • 약어 자제 ('qty'보다 '수량'). 전체 모델에서 유일한 이름.
도메인(Domain)

속성이 가질 수 있는 값의 종류·범위·제약. 데이터 타입 + 크기 + 허용값(제약) 세 가지가 모두 포함되며, NULL 허용 여부도 도메인의 일부.

성별 = CHAR(1) / {'M','F'}만 허용 · 나이 = NUMBER(3) / 0~150 · 이메일 = VARCHAR2(100) / @ 포함

SQL 실전 — 파생 속성 & 도메인(CHECK)

CREATE TABLE MEMBER ( MEMBER_ID VARCHAR2(10), -- 설계 속성 NAME VARCHAR2(50), -- 기본 속성 BIRTH DATE, -- 기본 속성 AGE NUMBER GENERATED ALWAYS AS -- 파생 속성(자동 계산) (TRUNC(MONTHS_BETWEEN(SYSDATE, BIRTH)/12)) VIRTUAL ); -- 도메인을 제약조건(CHECK)으로 표현 CREATE TABLE SURVEY ( GENDER CHAR(1) CHECK(GENDER IN('M','F')), -- 허용값 도메인 AGE NUMBER(3) CHECK(AGE BETWEEN 0 AND 150) NOT NULL );

5. 관계 (Relationship)

정의

관계란 두 엔터티가 서로 어떻게 연결되어 있는지 표현한 것이다.

ex) '회원 ─ 주문 : 주문하다/주문되다', '부서 ─ 사원 : 소속하다/소속되다'처럼 양방향 동사로 표현한다.

관계의 4요소

요소영문설명예
관계명Membership두 엔터티를 잇는 동사·역할명주문하다 / 주문되다
관계차수Cardinality1:1, 1:N, M:N회원 1 : N 주문
관계선택성Optionality필수(Mandatory) / 선택(Optional)주문엔 반드시 회원이 있어야 하나?
관계방향Direction양방향 표현(양쪽 관계명 모두 명명)회원→주문 / 주문→회원

관계 차수(Cardinality) 3가지

차수의미예
1 : 1서로 하나씩사원 ─ 사원증 (사원 1명당 사원증 1개)
1 : N한쪽이 하나일 때 상대는 여럿부서 ─ 사원, 회원 ─ 주문
M : N양쪽 모두 여럿 → 그대로 구현 불가학생 ─ 과목
!

M:N 해소  M:N은 그대로 둘 수 없어 중간에 연결(교차) 엔터티를 두어 1:N + N:1로 분해합니다. (학생 ─ 수강 ─ 과목)

관계 선택성(Optionality) & 식별 vs 비식별

구분표기의미
필수 (Mandatory)| (막대)반드시 있어야 함 — [회원]──[주문]: 주문엔 반드시 회원
선택 (Optional)○ (고리)있을 수도 없을 수도 — [회원]──○[쿠폰]: 쿠폰은 없을 수도

식별 관계 (실선)

자식의 PK에 부모 식별자가 포함(강한 종속). 자식이 부모 없이 존재 불가. (주문 ↔ 주문상세)

비식별 관계 (점선)

부모 식별자가 자식의 일반 속성(FK)으로만. 자식이 부모 없이도 존재 가능. (부서 ↔ 사원)

SQL 실전 — 관계는 외래키(FK)로 구현된다

CREATE TABLE ORDERS ( ORDER_ID NUMBER PRIMARY KEY, MEMBER_ID VARCHAR2(10), -- 외래키(관계의 구현) CONSTRAINT FK_ORDER_MEMBER FOREIGN KEY(MEMBER_ID) REFERENCES MEMBER(MEMBER_ID) ); -- 관계는 곧 조인이 된다 (설계의 1:N → ON 한 줄) SELECT M.NAME, O.ORDER_ID FROM MEMBER M JOIN ORDERS O ON M.MEMBER_ID = O.MEMBER_ID;

6. 식별자 (Identifier)

정의

식별자란 엔터티 안의 인스턴스를 서로 구분해 주는 유일한 표식이다. 테이블의 기본키(PK)가 된다.

ex) 같은 이름의 김철수가 100명 있어도 주민등록번호는 모두 다르다. 이름은 일반 속성, 주민번호는 식별자. PK는 자기 엔터티의 식별자, FK(외부식별자)는 다른 엔터티의 PK를 참조한 식별자.

주식별자의 4가지 조건 — '유·최·불·존'

1

유일성

모든 인스턴스를 유일하게 구분.

2

최소성

꼭 필요한 속성만으로 구성 (정규화와 직결).

3

불변성

한 번 정해지면 거의 변하지 않음.

4

존재성

NULL이 될 수 없음 (NOT NULL).

★

참고  PRIMARY KEY 제약은 유일성 + NOT NULL을 한꺼번에 강제 → 4조건 중 2가지가 DBMS 차원에서 자동 보장. ('대표성'은 아래 분류 기준의 개념으로, 교재에 따라 특성에 함께 넣기도 함)

식별자의 4가지 분류 기준

기준분류핵심 차이
① 대표성주식별자 / 보조식별자엔터티 대표 식별자(회원ID) vs 보조용(이메일·UNIQUE)
② 생성 여부내부식별자 / 외부식별자자기 엔터티에서 생성 vs 다른 엔터티 PK를 가져옴(= FK)
③ 속성 수단일식별자 / 복합식별자1개 속성 vs 2개 이상 결합 (주문ID+상품ID)
④ 대체 여부본질식별자 / 인조식별자업무 자연 도출(주민번호·학번) vs 인위적 부여(자동증가·UUID)

SQL 실전 — PK / FK / 복합키

-- 회원: 단일 PK + 보조식별자(UNIQUE) CREATE TABLE MEMBER ( MEMBER_ID VARCHAR2(10) PRIMARY KEY, -- 주식별자 EMAIL VARCHAR2(100) UNIQUE, -- 보조식별자 NAME VARCHAR2(50) NOT NULL ); -- 주문상세: 복합 PK (ORDER_ID + PROD_ID) CREATE TABLE ORDER_DETAIL ( ORDER_ID NUMBER, PROD_ID VARCHAR2(10), QTY NUMBER, CONSTRAINT PK_OD PRIMARY KEY(ORDER_ID, PROD_ID) -- 복합 식별자 ); INSERT INTO MEMBER VALUES('M01', 'a@a.com', '김철수'); INSERT INTO MEMBER VALUES('M01', 'b@b.com', '박민수'); -- 에러! 유일성 위반(ORA-00001) INSERT INTO MEMBER VALUES(NULL, 'c@c.com', '이영희'); -- 에러! 존재성 위반(ORA-01400)

데이터 모델과 SQL

정규화·관계와 조인·트랜잭션·NULL·식별자가 실제 SQL로 어떻게 이어지는지 다룹니다. 정규화 단계 구분과 관계=FK=JOIN 흐름은 거의 매번 출제됩니다.

1. 정규화 (Normalization)

정의

정규화란 데이터의 중복을 없애고 이상현상을 막기 위해 테이블을 단계적으로 쪼개는 작업이다.

ex) 옷장 한 칸에 속옷·양말·셔츠를 다 욱여넣으면 찾기 어렵고 하나 빼다 다른 게 떨어진다. 칸을 종류별로 나누는 것이 정규화.

정규화하면 입력·수정·삭제 성능은 일반적으로 향상, 조회 성능은 조건에 따라 향상되거나 저하(조인 증가). 중복 제거 → 무결성↑, 저장공간↓.

이상현상 (Anomaly) 3가지 — 정규화가 막으려는 것

삽입 이상

데이터를 넣으려는데 다른 정보가 없어 못 넣음. (학생 등록하려는데 수강과목 칸을 비울 수 없음)

갱신 이상

한 곳만 바꿨는데 다른 곳이 안 바뀜. (회원 주소 1곳만 수정 → 데이터 불일치)

삭제 이상

데이터를 지우려다 필요한 정보까지 사라짐. (마지막 수강 취소했는데 학생 정보까지 삭제)

정규화 단계 한눈에 — 뒤로 갈수록 엄격해진다

자주 틀리는 함정

함정3정규화는 주식별자와 일반 속성 사이의 종속을 없애는 것이다.
바로잡기3NF는 일반 속성끼리의 이행 종속 제거. 주식별자와의 부분 종속은 2NF.
함정정규화를 하면 성능이 무조건 나빠진다.
바로잡기조회는 불리할 수 있으나 입력·수정·삭제와 정합성은 좋아진다.
⏱ 30초 정리

1NF 원자값(한 칸 한 값) → 2NF 부분종속 제거(복합키 일부 딸림) → 3NF 이행종속 제거(일반속성 간) → BCNF 모든 결정자=후보키. 정규화=저장 분산·조회 조인, 반정규화는 그 반대.

2. 반정규화 (De-Normalization) 보충

조회 성능을 위해 중복을 허용하거나 그룹핑하는 과정. 정규화가 끝난 뒤 성능 이슈가 있을 때만 고려합니다.

조회 성능 ↑, 그러나 입력·수정·삭제 성능 ↓ + 정합성(무결성) 저해 위험. 신중해야 합니다.

구분기법
테이블 반정규화병합(1:1, 1:M) / 분할(수직·수평) / 추가(중복·통계·이력·부분)
컬럼 반정규화중복 컬럼 추가 / 파생 컬럼 추가 / 이력 테이블 컬럼 추가
관계 반정규화중복 관계 추가
수직 분할

일부 속성(컬럼)을 별도 테이블로 → 1:1 관계 2개. (자주 쓰는 컬럼 / NULL 많은 컬럼 분리)

수평 분할

일부 인스턴스(행)를 기준(주로 기간)으로 분할 = 파티셔닝.

3. 관계와 조인의 이해 관계=FK=JOIN

정의

모델에서의 관계는 외래키(FK)로 구현되고, 그 관계를 따라 여러 테이블을 합쳐 보는 작업이 조인(JOIN)이다.

ex) 영수증엔 주문만, 회원카드엔 회원만 있다. 같은 사람 것을 맞춰 보면 "김철수가 사과 2개 샀구나"가 보인다 — 키로 맞춰 합치는 것이 조인.
1

관계 (설계·개념 모델)

두 엔터티의 의미적 연결("회원이 주문을 한다")을 ERD 선으로 표현.

2

외래키 FK (논리·물리 모델)

자식 테이블이 부모 테이블의 PK를 참조하는 컬럼. FK = 조인 키.

3

조인 JOIN (SQL 실행)

FK = PK 조건으로 두 테이블을 합쳐 한 결과로 조회.

바로잡기키가 전파되지 않아 상위 엔터티까지 가려면 조인이 더 필요해진다.
⏱ 30초 정리

관계=FK=JOIN. 조인=PK·FK 값 일치. 1:N 조인 결과 행 수는 N쪽 수만큼. 교차 엔터티 생략=카티션 곱. Arc(상호배타)=여럿 중 하나와만.

4. 모델이 표현하는 트랜잭션의 이해

정의

트랜잭션이란 함께 성공하거나 함께 실패해야 하는 데이터 작업의 묶음이다. 모델은 이 묶음을 관계의 필수성과 식별성으로 표현한다.

ex) 계좌 이체는 A에서 1만원 출금 + B에 1만원 입금이 한 묶음. A에서만 빠지고 멈추면 돈이 사라지므로, 둘 다 성공하거나 둘 다 취소되어야 한다.

트랜잭션 4대 특징 — ACID (원·일·고·지)

원자성 (Atomicity)

모두 성공하거나 모두 실패 — 이체는 출금+입금 한 묶음.

일관성 (Consistency)

트랜잭션 전후 무결성 규칙 유지 — 잔고 합계는 변하지 않음.

고립성 (Isolation)

동시 실행이라도 서로 간섭 없음 — 다른 사람 이체와 겹치지 않음.

지속성 (Durability)

커밋되면 시스템이 죽어도 보존 — 영수증으로 기록됨.

트랜잭션 상태 흐름

⏱ 30초 정리

ACID = 원자·일관·고립·지속. 양쪽 필수(식별) 관계 = 한 트랜잭션. 미커밋 값 읽기 = 고립성 위반, 커밋 후 유실 = 지속성 위반. SAVEPOINT = 일부만 롤백.

정의

6. 본질식별자 vs 인조식별자

정의

본질식별자는 업무에서 자연스럽게 도출된 식별자, 인조식별자는 인위적으로 만든 식별자다. 둘의 장단점을 알고 상황에 맞게 선택한다.

ex) 도서관에서 ISBN(출판사 부여=본질식별자)과 자체 분류번호 A-001(임의 부여=인조식별자)로 책을 구분. ISBN이 길고 형식이 들쑥날쑥해 자체 번호를 더 자주 쓴다.

본질식별자 (Natural)

업무에서 자연 도출 · 의미 있음 · 변경 위험 존재. (주민번호·사업자번호·ISBN)

인조식별자 (Surrogate)

인위적으로 부여 · 의미 없음 · 변경에 자유. (자동증가 ID·UUID·GUID)

비교표

항목본질식별자인조식별자

현업 권장

PK는 인조식별자(짧은 ID)로 두고, 본질키는 UNIQUE 제약으로 별도 보존 → 보안·성능·일관성을 모두 만족.

TRUNC(수[,자리])버림(절삭)TRUNC(54.29,1) → 54.2
CEIL올림(크거나 같은 최소 정수)CEIL(72.1) → 73
FLOOR내림(작거나 같은 최대 정수)FLOOR(72.9) → 72
MOD(수1,수2)나머지 (수2가 0이면 수1 반환)MOD(15,7) → 1
!

헷갈림 주의  음수에서 CEIL(-33.4)=-33(올림이니 0에 가까움), FLOOR(-22.3)=-23(내림이니 더 작게). MOD(n,0)=n 꼭 기억!

1. 서브쿼리 (Subquery)

편리성

복잡한 쿼리를 뷰 이름으로 단순화.

보안성

!

4. 그룹 함수 (ROLLUP · CUBE · GROUPING SETS)

소계(소그룹별 합)와 총계를 구하는 함수들입니다. 이게 SQL 활용에서 제일 어렵지만, "무엇으로 그룹핑되는가"만 비교하면 됩니다.

함수그룹핑 결과 (A, B 기준)
ROLLUP(A,B)①A,B별 ②A별 ③총계  (한 방향 소계)
CUBE(A,B)①A,B별 ②A별 ③B별 ④총계  (모든 조합)
GROUPING SETS(A,B)①A별 ②B별  (지정한 것만, 총계 없음)
💡 핵심 직관

ROLLUP = 계단식 소계(왼→오 한 방향). CUBE = 가능한 모든 조합의 소계(다차원). GROUPING SETS = 내가 지정한 묶음만 개별 집계. 총계가 필요하면 인자에 ()를 추가하거나 ROLLUP을 쓰면 됩니다.

!

시험 포인트  괄호 묶음은 "한 덩어리"로 취급. ROLLUP((A,B), C) → (A,B),C별 → (A,B)별 → 총계. "결합 가능한 모든 집계" = CUBE.

❓ 확인 퀴즈 · 집합 연산자
차집합과 같은 역할을 하는 집합 연산자는?
정답 ② 차집합 = MINUS(Oracle) / EXCEPT(SQL Server). 교집합은 INTERSECT.
2과목 · PART 2-3

관리 구문

SQL 명령어를 4종류로 나눠 익힙니다. DML·TCL·DDL·DCL — 어느 명령어가 어디 속하는지가 단골 출제 포인트입니다.

분류풀이명령어
DML데이터 조작어INSERT, UPDATE, DELETE, (SELECT), MERGE
TCL트랜잭션 제어어COMMIT, ROLLBACK, SAVEPOINT
DDL데이터 정의어CREATE, ALTER, DROP, RENAME, TRUNCATE
DCL데이터 제어어GRANT, REVOKE (+ CREATE/ALTER/DROP USER)
★

암기팁  헷갈리는 두 가지: COMMIT/ROLLBACK은 TCL(DDL 아님!), TRUNCATE는 DDL(DML 아님!). GRANT/REVOKE는 DCL.

1. DML — 데이터 조작어

명령어설명주의
INSERT데이터 입력PK·NOT NULL 컬럼엔 NULL 입력 불가
UPDATE데이터 수정WHERE 없으면 전체 행 수정
DELETE데이터 삭제WHERE 없으면 전체 행 삭제. COMMIT 전 ROLLBACK 가능
MERGE입력+수정을 한 번에 (ON 조건으로 MATCHED/NOT MATCHED 분기)동기화·백업에 유용
🔎 DELETE vs TRUNCATE vs DROP

DELETE: 행만 삭제, ROLLBACK 가능, 로그 남김. TRUNCATE: 전체 행 삭제 + 저장공간 초기화, ROLLBACK 불가(DDL), 빠름, 구조는 유지. DROP: 테이블 구조까지 통째 삭제. "연인과 깔끔히 헤어지는 TRUNCATE, 미련 남기는 DELETE"로 기억!

!

시험 포인트  1억 건을 로그 없이 빠르게 비우고 테이블은 유지 → TRUNCATE. DML은 COMMIT해야 디스크 반영(단 SQL Server는 DML도 AUTO COMMIT).

2. TCL — 트랜잭션 제어어

명령어설명
COMMIT변경 내용 확정·반영. 해야 최종 저장
ROLLBACK변경 내용 취소, 이전 값 복구
SAVEPOINT중간 지점 저장 → ROLLBACK TO 지점으로 일부만 되돌림
★

핵심  COMMIT 전까지는 메모리에만 있어 다른 사용자는 못 봄. 오래 COMMIT/ROLLBACK 안 하면 LOCK이 걸려 남이 수정 못 함.

3. DDL — 데이터 정의어

데이터 유형 — CHAR vs VARCHAR

CHAR (고정 길이)

정한 크기를 항상 다 차지. 'IU'를 CHAR(10)에 넣으면 10byte. 비교 시 공백 무시 → 'IU'='IU  '.

VARCHAR (가변 길이)

실제 크기만 사용. 'IU'는 2byte. 비교 시 공백도 문자 → 'IU'≠'IU  '.

※ 영어 1글자=1byte, 한글 1글자=3byte(캐릭터셋에 따라 2byte)로 크기를 계산.

주요 명령어

명령어설명
CREATE TABLE테이블 생성 (컬럼·데이터유형·크기·제약조건 정의)
ALTER ... ADD컬럼/제약조건 추가 (컬럼은 항상 맨 끝에)
ALTER ... MODIFY데이터유형·DEFAULT·NOT NULL 변경
ALTER ... DROP COLUMN컬럼 삭제 (복구 불가)
ALTER ... RENAME COLUMN컬럼명 변경
DROP TABLE테이블 삭제. 참조 테이블 있으면 CASCADE CONSTRAINT 필요
TRUNCATE TABLE전체 행 삭제 + 공간 초기화 (ROLLBACK 불가)
🔎 CTAS & 제약조건

CTAS(CREATE TABLE ~ AS SELECT ~): 기존 테이블 복사 생성. 단 NOT NULL만 복사되고 PK·UNIQUE·CHECK는 초기화 → 필요 시 ALTER로 재정의. 제약조건: PRIMARY KEY, UNIQUE, NOT NULL, CHECK(값 범위 지정), FOREIGN KEY(참조 무결성).

!

시험 포인트  컬럼 데이터유형/DEFAULT/NOT NULL 변경 → MODIFY. 컬럼 추가 → ADD. CASCADE는 Oracle만 있고 SQL Server엔 없음.

4. DCL — 데이터 제어어

💡 쉽게 말하면

DB를 '집'이라 하면 USER는 '룸메이트'. 먼저 사람을 들이고(CREATE USER + 비밀번호), 집을 쓸 권한을 줘야(GRANT) 방에 들어갈 수 있어요. 권한 회수는 REVOKE.

명령어설명
GRANT 권한 TO 사용자권한 부여 (예: GRANT CREATE TABLE TO PERPEAR)
REVOKE 권한 FROM 사용자권한 회수
ROLE여러 권한을 하나로 묶은 세트 (빅맥세트처럼). ROLE을 사용자에게 GRANT
❓ 확인 퀴즈 · 명령어 분류
다음 중 DDL이 아닌 것은?
정답 ② COMMIT은 TCL. DDL은 CREATE·ALTER·DROP·RENAME·TRUNCATE입니다.

꼭 나오는 SQL 보충

교안에는 간략했지만 기출에 반드시 나오는 조인·계층형 쿼리·윈도우 함수·연산자 우선순위·CASE를 한 번에 정리했습니다. 2과목 고득점의 열쇠입니다.

1. JOIN (조인)

두 테이블을 연결해 조회합니다. 결과 건수를 묻는 문제가 자주 나옵니다.

종류설명
INNER JOIN양쪽에 모두 있는 행만 (교집합)
LEFT OUTER왼쪽 전부 + 매칭되는 오른쪽 (없으면 NULL)
RIGHT OUTER오른쪽 전부 + 매칭되는 왼쪽
FULL OUTER양쪽 전부 (매칭+비매칭 모두)
CROSS JOIN두 테이블 행의 곱 (카테시안 곱)
!

시험 포인트  ① INNER JOIN에서 ON이 빠지면 CROSS JOIN과 같은 결과(행의 곱). ② Oracle의 (+)는 ANSI OUTER JOIN으로 변환되는데, (+)가 왼쪽에 있으면 RIGHT OUTER, 오른쪽에 있으면 LEFT OUTER. ③ USING·NATURAL JOIN의 공통 컬럼엔 테이블명/별칭을 붙이지 않음.

🔎 건수 계산 예

A테이블 4행, B테이블 3행, 공통 2건이면 → INNER 2, LEFT 4, RIGHT 3(공통2+B단독1 형태에 따라), FULL 5, CROSS 4×3=12. 벤다이어그램으로 "어느 쪽을 다 살리나"를 떠올리세요.

2. 계층형 쿼리 (Hierarchical Query)

조직도·게시판 댓글처럼 부모-자식 구조를 조회합니다 (SELF JOIN 형태).

SELECT LEVEL, 사원 FROM 사원테이블 START WITH 상위사원 IS NULL -- 루트(시작점) CONNECT BY PRIOR 사원 = 상위사원; -- 부모→자식 전개
구문의미
LEVEL현재 깊이(Depth). 루트=1. 리프가 가장 큰 값
START WITH시작(루트) 노드 지정
CONNECT BY부모-자식 연결 규칙. PRIOR 위치로 순/역방향 결정
SYS_CONNECT_BY_PATH루트부터 현재까지 경로 출력
CONNECT_BY_ROOT최상위 루트 값 표시
CONNECT_BY_ISLEAF최하위(리프)면 1, 아니면 0
NOCYCLE순환(CYCLE) 발생 시 멈춤
!

시험 포인트  ① PRIOR 위치에 따라 순방향/역방향 전개 가능. ② WHERE는 START WITH…CONNECT BY로 전개가 끝난 뒤 필터링. ③ TRIM은 계층형 함수가 아님(함정). ④ 동일 레벨 정렬은 ORDER SIBLINGS BY.

3. 윈도우 함수 (Window Function)

행을 그룹으로 묶지 않고도 그룹별 계산·순위를 각 행 옆에 보여줍니다. OVER()가 핵심.

SELECT 사원, 급여, RANK() OVER(PARTITION BY 부서 ORDER BY 급여 DESC) 순위 FROM 사원; -- 부서별로 급여 높은 순 순위

순위 함수 (★빈출)

함수동점 처리 (1,1 다음)
RANK동점은 같은 순위, 다음은 건너뜀 (1,1,3)
DENSE_RANK동점은 같은 순위, 다음은 안 건너뜀 (1,1,2)
ROW_NUMBER동점도 무조건 순차 (1,2,3)

기타 함수 & 윈도우 범위

구문의미
FIRST_VALUE / LAST_VALUE정렬 후 첫 / 마지막 값
LAG / LEAD이전 / 다음 행 값
RATIO_TO_REPORT파티션 합계 중 비율
CUME_DIST / PERCENT_RANK누적 백분율 (0~1)
NTILE(n)n개 등급으로 분할
ROWS / RANGE행 자체 기준 / 값 기준
UNBOUNDED PRECEDING시작점에만 사용(파티션 첫 행)
UNBOUNDED FOLLOWING끝점에만 사용(파티션 마지막 행)
!

시험 포인트  RANK vs DENSE_RANK 차이(건너뛰기 유무)가 단골. UNBOUNDED PRECEDING은 끝점에 못 옴. 비율 함수(CUME_DIST·PERCENT_RANK·RATIO_TO_REPORT)는 0~1 범위.

4. 연산자 우선순위 · SQL 실행 순서

연산자 우선순위

산술 → 연결(||) → 비교 → IN·LIKE·BETWEEN·IS NULL → NOT → AND → OR

SQL 실행 순서

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY

★

암기팁  실행 순서: "프 → 웨 → 그 → 하 → 셀 → 오". SELECT는 거의 마지막, ORDER BY가 진짜 마지막. 작성 순서와 실행 순서가 다른 점이 함정!

5. CASE · DECODE · 기타 자주 나오는 것

구문설명
CASE WHEN 조건 THEN … ELSE … ENDIF-THEN-ELSE 논리. 범위 조건 가능
DECODE(컬럼, A, 결과1, 기본값)Oracle 전용. = 비교만 가능
NULL 비교반드시 IS NULL / IS NOT NULL (CASE로 =NULL 비교 불가!)
ANY / ALLANY=하나라도 만족, ALL=모두 만족 (다중행)

순수 관계 연산자SELECT, PROJECT, JOIN, DIVIDE

SQL문의 실행 순서로 올바른 것은?
정답 ① FROM으로 테이블 선택 → WHERE 필터 → GROUP BY/HAVING 그룹 → SELECT 인출 → ORDER BY 정렬.

6. GROUP BY · HAVING

데이터를 묶어서 집계(합계·평균·개수 등)할 때 씁니다.

SELECT 부서, COUNT(*) FROM 사원 WHERE 급여 > 3000 -- ① 그룹 전 행 필터 GROUP BY 부서 -- ② 부서별로 묶기 HAVING COUNT(*) >= 5; -- ③ 그룹 후 조건
!

시험 포인트  ① WHERE는 그룹 전, HAVING은 그룹 후 필터. ② SELECT에 집계함수와 함께 쓴 일반 컬럼은 반드시 GROUP BY에 들어가야 함. ③ 집계함수(SUM/AVG/COUNT(컬럼))는 NULL 제외, COUNT(*)만 NULL 포함.

7. 조인 보충 — SELF · NATURAL · ANSI

조인설명
SELF JOIN한 테이블을 자기 자신과 조인 (별칭 2개 사용). 사원-상사 관계 등
NATURAL JOIN두 테이블의 같은 이름·타입 컬럼을 자동으로 EQUI JOIN. 공통 컬럼에 테이블명·별칭 붙이면 안 됨
USING공통 컬럼 중 원하는 것만 골라 조인. 역시 별칭 금지
ON조인 조건을 직접 지정 (컬럼명 달라도 가능)
★

Oracle (+) ↔ ANSI 변환  (+)가 왼쪽에 있으면 → RIGHT OUTER JOIN, 오른쪽에 있으면 → LEFT OUTER JOIN. 기호 반대쪽을 다 살린다고 기억!

8. TOP-N 쿼리 (상위 N건 조회)

방식문법
Oracle ROWNUMWHERE ROWNUM <= 5 (정렬이 필요하면 인라인 뷰로 ORDER BY 먼저)
ANSI FETCHORDER BY 급여 DESC FETCH FIRST 5 ROWS ONLY
OFFSET … FETCHOFFSET 10 ROWS FETCH NEXT 5 ROWS ONLY (11~15위)
SQL Server TOPSELECT TOP 5 …
!

함정 주의  WHERE ROWNUM <= 5 ORDER BY ...는 정렬 전에 5건을 잘라버려 원하는 상위 5건이 아닐 수 있음. 반드시 정렬된 인라인 뷰를 먼저 만든 뒤 ROWNUM을 걸어야 합니다.

9. PIVOT / UNPIVOT

PIVOT

행 → 열로 회전. 세로로 쌓인 데이터를 가로 표(교차표)로 집계. (예: 월별 매출을 '1월·2월·3월' 컬럼으로)

UNPIVOT

열 → 행으로 되돌림. 가로로 펼쳐진 컬럼을 세로 데이터로 변환.

💡 쉽게 말하면

엑셀 '피벗 테이블'과 같은 개념이에요. PIVOT = 세로 목록을 가로 요약표로, UNPIVOT = 그 반대. 방향만 기억하면 됩니다.
