데이터 모델링의 이해

현실의 업무를 데이터베이스로 옮기는 설계 단계입니다. 1과목은 10문항뿐이지만 용어 구분(엔터티·속성·관계·식별자)만 잡으면 빠르게 득점할 수 있습니다. 처음이라면 이 챕터를 가장 천천히 읽으세요.

1. 데이터 모델링이란

현실 세계의 업무를 약속된 규칙(표기법)으로 그려 데이터베이스 구조로 옮기는 설계 작업입니다.

💡 쉽게 말하면

데이터 모델링은 현실을 지도로 그리는 일이에요. 실제 도시엔 건물·사람·차가 가득하지만 지도엔 길과 주요 건물만 간단히 그리죠. 똑같이, 복잡한 회사 업무에서 "저장·관리할 정보"만 골라 깔끔한 그림으로 옮기는 게 데이터 모델링입니다. 집을 짓기 전에 설계도부터 그리는 것과 같습니다.

왜 하나요? — 모델링을 안 하면 생기는 3가지 문제

문제 1

중복

같은 정보가 여기저기 저장돼 저장공간을 낭비하고 관리가 어려워집니다.

문제 2

비일관성

한 곳만 고치고 다른 곳을 놓쳐 값이 서로 안 맞게 됩니다(정합성 깨짐).

문제 3

비유연성

구조가 뒤엉켜 작은 업무 변경에도 전체를 손봐야 합니다.

데이터 모델링은 이 세 가지를 막기 위해, 업무 데이터를 중복 없이·일관되게·바꾸기 쉽게 정리하는 작업입니다.

데이터 모델링의 3가지 특징 — '추·단·명'

특징 1

추상화

공통된 특징을 뽑아 간략하게. 핵심만 남깁니다.

특징 2

단순화

복잡함을 피하고 누구나 이해할 수 있게 표현합니다.

특징 3

명확화

해석이 모호하지 않게, 한 가지 의미만 갖도록 합니다.

2. 데이터 모델링 3단계 — 개념 → 논리 → 물리

모델링은 추상적인 밑그림에서 시작해 점점 구체적인 DB 구조로 좁혀갑니다. 뒤로 갈수록 기술적·구체적이 됩니다.

1단계 · 개념적

개념적 모델링

전사(업무 전체) 관점. 추상화 수준이 가장 높음. 중요한 엔터티·관계만 뽑아 개념 ERD를 그립니다.

2단계 · 논리적

논리적 모델링

식별자·속성·관계를 정확히 표현하고 정규화로 중복을 제거합니다. 특정 DBMS에 독립적인, 모델링의 핵심 완성 단계.

3단계 · 물리적

물리적 모델링

실제 DB에 맞춰 테이블·컬럼·인덱스를 설계. 성능·보안·저장을 고려한 최종 구축 단계.

개념적핵심 엔터티·관계
→
논리적속성·식별자·정규화
→
물리적테이블·인덱스·성능
🏠 집 짓기로 비유

개념적 = '방3·거실1' 손스케치 → 논리적 = 치수·배관까지 그린 설계도면 → 물리적 = 벽돌로 실제 시공. 설계(개념·논리)가 탄탄해야 시공(물리)에서 고생하지 않습니다.

!

시험 포인트  "추상화 수준이 가장 높다" → 개념적. "특정 DBMS에 독립적, 정규화 수행" → 논리적. "인덱스·성능·실제 테이블 생성" → 물리적.

3. 데이터 모델링의 3가지 관점

같은 업무라도 무엇에 초점을 두고 보느냐에 따라 세 관점으로 나뉩니다.

관점초점분석 활동
데이터 관점업무에서 쓰는 데이터는 무엇인가구조 분석(정적 분석)
프로세스 관점업무에서 하는 일은 무엇인가시나리오 분석(동적 분석)

!

시험 포인트  "CRUD 매트릭스" 또는 "데이터와 프로세스의 상관"이 보이면 → 데이터+프로세스 관점. CRUD = Create(생성)·Read(조회)·Update(수정)·Delete(삭제).

4. 3층 스키마 (데이터 독립성)

사용자·설계자·개발자가 DB를 보는 관점을 3단계로 나눈 ANSI 표준. 목적은 데이터 독립성 확보입니다.

🎬 쉽게 말하면

영화관에서 관객은 스크린만(외부), 기획자는 전체 구성을(개념), 영사기사는 필름 작동을(내부) 봅니다. 관점을 나눠두면 한쪽이 바뀌어도 다른 쪽이 흔들리지 않습니다.

스키마관점내용
외부 스키마사용자 관점사용자 뷰(View). 각자 필요한 데이터만 보는 창.
개념 스키마설계자 관점조직 전체가 공유하는 통합 구조. 모든 규칙·관계.
내부 스키마개발자 관점물리적 저장구조 — 저장·레코드·필드·인덱스.
논리적 독립성

개념 스키마가 바뀌어도 외부 스키마(사용자 뷰)는 영향 없음. 테이블에 컬럼을 추가해도 기존 화면은 그대로.

물리적 독립성

내부 스키마(저장·인덱스)가 바뀌어도 개념 스키마는 영향 없음. 디스크를 바꿔도 테이블 설계는 그대로.

!

시험 포인트  "물리적 저장구조·인덱스" → 내부. "사용자 뷰" → 외부. "전체 통합 설계" → 개념. 독립성은 논리적·물리적 두 가지.

5. ERD 작성 절차 시험 단골

ERD(Entity-Relationship Diagram)는 엔터티와 관계를 그리는 표준 그림(1976년 피터 첸 고안)입니다. 작성은 6단계 순서로 진행되며 이 순서가 그대로 출제됩니다.

1

엔터티를 그린다

업무에서 관리할 집합(덩어리)을 도출합니다.

2

엔터티를 적절히 배치한다

가장 중요한 엔터티를 왼쪽 상단에 둡니다.

3

엔터티 간 관계를 설정한다

연관되는 엔터티끼리 선을 긋습니다.

4

관계명을 기술한다

관계에 '주문하다' 같은 이름을 붙입니다.

5

관계 참여도(차수)를 기술한다

서로 몇 개씩 참여하는지(예: 고객 1 : 계좌 N).

6

관계의 필수 여부를 기술한다

반드시 있어야 하는 관계인지(필수/선택) 표시합니다.

★

암기팁  "누가 있나(1·2) → 어떻게 잇나(3) → 이름(4) → 몇 개(5) → 필수(6)". 관계 3종(관계명 → 참여도 → 필수)은 항상 뒤쪽에 옵니다.

❓ 확인 퀴즈 · ERD 절차
ERD 작성 절차로 올바른 것은? (ㄱ엔터티도출 · ㄴ배치 · ㄷ관계설정 · ㄹ관계명 · ㅁ참여도 · ㅂ필수여부)
정답 ① 도출 → 배치 → 관계설정 → 관계명 → 참여도 → 필수여부. 뒤 3개(관계명·참여도·필수)의 순서를 헷갈리지 마세요.

6. 엔터티 (Entity) 최빈출

업무에서 관리해야 할 정보의 덩어리(명사). 실제로는 테이블이 됩니다.

📦 쉽게 말하면

쇼핑몰이라면 회원·상품·주문·배송 같은 명사 하나하나가 엔터티예요. 엔터티는 엑셀 시트 한 장의 제목('회원' 시트), 그 안의 한 줄 한 줄이 인스턴스(행), 열 제목이 속성입니다.

엔터티 · 속성 · 인스턴스의 관계

📋 집합

엔터티 = 테이블

정보의 덩어리. 예: 회원(MEMBER)

🏷️ 항목

속성 = 컬럼

세부 항목. 회원ID · 이름 · 전화번호

📄 한 건

인스턴스 = 행

개별 사례. C001 · 김철수 · 010-1111

ER 다이어그램 — 회원(MEMBER) 1 : N 주문(ORDER)

표 전체가 엔터티(MEMBER), 헤더가 속성, 각 행이 인스턴스입니다.

엔터티의 5가지 특징 — '업·식·인·속·관'

글자특징의미
업업무에서 필요관리할 가치가 있는 정보여야 한다
식식별 가능식별자로 각 건을 유일하게 구분할 수 있어야 한다
인인스턴스 2개 이상행이 2건 이상 존재해야 한다
속속성 2개 이상컬럼이 2개 이상이어야 한다
관관계 1개 이상다른 엔터티와 최소 1개의 관계를 가져야 한다
!

함정 주의  "엔터티는 속성이 1개여도 된다" → 틀림(2개 이상). "인스턴스가 1건이어도 된다" → 틀림(2건 이상). 개수 조건이 자주 함정으로 나옵니다.

엔터티의 분류 — 2가지 기준

① 유·무형 (형태 유무)
유형 엔터티
물리적 형태 있음 — 상품·사원·매장
개념 엔터티
개념적으로만 존재 — 부서·조직·학과
사건 엔터티
행위로 발생 — 주문·결제·출입기록
② 발생 시점
기본(키) 엔터티
다른 엔터티 없이도 성립 — 사원·부서·고객
중심 엔터티
기본에서 발생, 업무 중심 — 주문·계약·매출
행위 엔터티

발생 시점 — 기본에서 중심, 다시 행위로 파생

기본(키) 엔터티스스로 성립 · 사원·부서
→
중심 엔터티기본에서 발생 · 주문·계약
→
행위 엔터티관계에서 발생 · 주문상세
!

헷갈림 주의  사건 엔터티는 '유·무형' 분류 쪽입니다. '발생 시점' 분류는 기본·중심·행위. "발생 시점이 아닌 것?" → 사건 엔터티. "주문은 기본 엔터티다" → 틀림(고객·상품에서 발생하므로 중심 엔터티).

SQL 실전 — 엔터티는 테이블이 된다

회원 엔터티를 실제 테이블로 만들고, 인스턴스(행)를 넣고, 조회해 봅니다.

-- ① 엔터티 → 테이블 생성 (CREATE) CREATE TABLE MEMBER ( MEMBER_ID VARCHAR2(10) PRIMARY KEY, -- 식별자(PK) NAME VARCHAR2(50), PHONE VARCHAR2(20), JOIN_DATE DATE ); -- ② 인스턴스(행) 입력 (INSERT) INSERT INTO MEMBER VALUES ('M01', '김철수', '010-1111', DATE '2026-01-15'); INSERT INTO MEMBER VALUES ('M02', '이영희', '010-2222', DATE '2026-02-08'); -- ③ 조회 (SELECT) SELECT MEMBER_ID, NAME FROM MEMBER;

7. 속성 (Attribute)

엔터티가 가지는 세부 항목. 더 이상 쪼갤 수 없는 의미의 최소 단위이며, 테이블의 컬럼이 됩니다.

  • 업무에서 관리되는 정보여야 한다.
  • 하나의 속성은 하나의 값만 가진다(원자값).
  • 주식별자에 함수적으로 종속된다(기본키가 정해지면 값이 하나로 결정됨).

속성의 분류

기준종류설명 (예)
특성에 따라기본 속성업무에서 그대로 가져온 것 (이름, 계좌번호)
설계 속성관리를 위해 새로 만든 것 (상품코드, 지점코드)
파생 속성다른 값에서 계산해 나온 것 (합계, 평균, 나이)

🔎 파생 속성 주의

파생 속성은 계산으로 얻어지므로, 중복 저장하면 원본이 바뀔 때 안 맞게 됩니다. 꼭 필요할 때만(성능상 이유) 두고, 보통은 조회 시 계산합니다.

도메인(Domain)

속성이 가질 수 있는 값의 범위·타입. 예: '성별'의 도메인은 {남, 여}, '나이'의 도메인은 0 이상의 정수. 제약조건(CHECK)으로 구현됩니다.

!

시험 포인트  "계산으로 얻는 값" → 파생 속성. "하나의 속성에 값이 여러 개" → 다중값 속성(1정규화 대상). "값의 범위" → 도메인.

8. 관계 (Relationship)

엔터티 사이의 연관성. "회원은 주문을 한다"처럼 엔터티를 이어줍니다.

존재 관계

상태로 엮임. 예: 사원이 특정 부서에 소속된다.

행위 관계

행동으로 엮임. 예: 고객이 상품을 주문한다.

관계 차수(Cardinality) — 몇 대 몇인가

차수의미예
1 : 1서로 하나씩 대응사원 ↔ 사원증
1 : N한쪽 하나에 상대는 여럿고객 1 → 주문 N
M : N양쪽 모두 여럿 → 해소 필요학생 ↔ 과목
🔎 M:N 관계 해소

학생 한 명이 여러 과목을, 한 과목에 여러 학생이 수강 → M:N. 이대로 두면 조인이 꼬이므로, 가운데에 교차(연결) 엔터티 '수강'을 넣어 학생 1:N 수강 N:1 과목으로 풉니다. 교차 엔터티는 두 부모의 식별자를 물려받습니다.

학생

수강교차 엔터티

과목

관계 읽는 법 (ERD 해석)

"한 명의 고객은 여러 개의 주문을 할 수 있다" → 고객 : 주문 = 1 : N, 선택적. 관계선을 양방향으로 한 문장씩 읽는 것이 요령입니다.

식별 관계 vs 비식별 관계

식별 관계 (실선)

부모의 기본키를 자식의 기본키 일부로 상속. 부모가 있어야 자식이 존재(강한 종속). 예: 주문ID를 주문상세의 PK 일부로.

비식별 관계 (점선)

부모의 기본키를 자식의 일반 속성(FK)으로만 참조. 부모 없이도 자식이 존재 가능(약한 종속). 예: 부서코드를 사원의 일반 컬럼으로.

ERD 표기법 — IE vs 바커

IE (정보공학 · 까마귀발)

다수(N)를 까마귀발로, 필수를 막대(|), 선택을 고리(○)로 표현. 가장 널리 쓰입니다.

바커(Barker)

관계선의 실선=필수, 점선=선택으로 선택성을 표현. Oracle 계열에서 사용.

!

시험 포인트  두 표기법 공통으로 까마귀발 = 다수(N). ○(고리) = 0개 가능(선택). 식별 관계는 실선(PK 상속), 비식별 관계는 점선(일반 FK).

9. 식별자 (Identifier)

엔터티의 각 인스턴스를 유일하게 구분하는 속성(또는 속성 묶음). 테이블의 기본키(PK)가 됩니다.

주식별자(기본키)의 4대 조건 — '유·최·대·불'

1

유일성

인스턴스를 유일하게 식별한다. (중복·NULL 불가)

2

최소성

유일성을 만족하는 최소한의 속성으로만 구성.

3

대표성

엔터티를 대표할 수 있어야 한다.

4

불변성

값이 자주 바뀌지 않아야 한다.

키설명

1. 정규화 (Normalization) 최빈출

데이터 정합성(정확성·일관성)을 위해 중복을 제거하고 테이블을 작은 단위로 나누는 과정입니다.

💡 쉽게 말하면

정규화는 '중복 정리정돈'이에요. 한 표에 같은 정보가 여기저기 반복되면 수정할 때 다 바꿔야 하고 실수가 생기죠. 그래서 겹치는 걸 떼어내 표를 쪼갭니다. 대신 표가 늘어나 조회 때 조인(JOIN)이 많아질 수 있어요.

함수적 종속 (Functional Dependency)

정규화를 이해하는 열쇠입니다. A → B 는 "A가 정해지면 B가 하나로 결정된다"는 뜻. 예) 회원ID → 회원명(회원ID가 같으면 이름도 같다). 이때 A를 결정자라고 부릅니다.

정규화 단계 — 표를 직접 쪼개보기

1

제1정규형 (1NF) — 원자값

모든 칸은 하나의 값만. 반복 그룹·다중값을 없앱니다. 예) '취미=등산,독서' → 한 칸에 하나씩 행을 나눔.

2

제2정규형 (2NF) — 부분함수 종속 제거

복합키(2개 이상)일 때, 키의 일부에만 딸린 속성을 분리. 예) PK=(주문번호,상품코드)인데 '상품명'이 상품코드에만 종속 → 상품 테이블로 분리.

3

제3정규형 (3NF) — 이행함수 종속 제거

키가 아닌 일반 속성끼리의 종속을 분리. 예) 회원등급 → 등급할인율(둘 다 일반 속성) → 등급 테이블로 분리.

BCNF (보이스-코드 정규형)

제3정규형을 더 강화한 단계. 모든 결정자가 후보키여야 한다는 규칙으로, "후보키가 아닌데 다른 속성을 결정하는" 결정자를 분리합니다. 정규화 순서는 1 → 2 → 3 → BCNF → 4 → 5이며, 시험에선 "3정규형보다 강한 정규형 = BCNF" 정도만 알면 됩니다.

정규화 ↔ 성능  입력·수정·삭제 성능은 일반적으로 향상(중복이 없으니 한 곳만 고침), 조회 성능은 향상되거나 저하(테이블이 늘어 조인이 많아지면 느려질 수 있음). 중복↓·무결성↑·저장공간↓.

!

시험 포인트  "정규화하면 조회 성능이 반드시 향상" → 틀림(조인 때문에 저하될 수 있음). 정규화할수록 테이블(엔터티)은 증가.

정규화에 대한 설명으로 틀린 것은?

❓ 확인 퀴즈 · 정규형 판별
PK가 (주문번호, 상품코드)인 테이블에서 '상품명'이 상품코드에만 종속되어 분리해야 한다. 어떤 정규화인가?
정답 ② 복합키의 일부(상품코드)에만 종속되는 부분함수 종속 → 제2정규화.

2. 반정규화 (De-Normalization)

조회 성능을 위해 의도적으로 중복을 허용하는 과정. 정규화를 끝낸 뒤 성능 문제가 있을 때만 신중히 적용합니다.

조회 성능 ↑, 그러나 입력·수정·삭제 성능 ↓ + 정합성(무결성) 저해 위험. 공짜가 아니라 '트레이드오프'입니다.

반정규화 기법

대상기법
테이블병합(1:1, 1:M) · 분할(수직·수평) · 추가(중복·통계·이력·부분)
컬럼중복 컬럼 추가 · 파생 컬럼 추가 · 이력 컬럼 추가
관계중복 관계 추가
수직 분할

일부 컬럼을 떼어 별도 테이블로 → 1:1 관계. 자주 안 쓰는 컬럼·NULL 많은 컬럼 분리.

수평 분할

일부 행을 기준(주로 기간)으로 분할 = 파티셔닝.

!

시험 포인트  수직=컬럼 분할(1:1), 수평=행 분할(파티셔닝). 테이블 추가 기법 = 중복·통계·이력·부분. '백업 테이블 추가'는 반정규화가 아님(함정).

슈퍼타입 / 서브타입 변환

공통 속성(슈퍼타입)과 개별 속성(서브타입)으로 나뉜 모델을 실제 테이블로 바꾸는 3가지 방식입니다.

방식구성특징

❓ 확인 퀴즈 · 반정규화
테이블 추가 반정규화 기법이 아닌 것은?
정답 ② 테이블 추가 기법 = 중복·통계·이력·부분. '백업'은 포함되지 않습니다.

3. 관계와 성능 — 식별 vs 비식별

식별/비식별 관계 선택은 성능에 직결됩니다. 자식이 부모 키를 PK로 물려받는 식별 관계가 쌓이면 PK가 계속 커져 조인·인덱스에 부담이 됩니다.

식별 관계가 많으면

자식 PK에 부모 키가 누적 → PK 컬럼 수↑, 인덱스 커짐. 단, 상위 키로 바로 조회 가능(조인 유리할 때도).

비식별 관계가 많으면

PK는 간결(FK는 일반 컬럼). 대신 상위 정보를 얻으려면 조인이 늘 수 있음.

!

시험 포인트  무조건 식별/비식별이 좋은 게 아니라 업무·조회 패턴에 따라 선택. 식별 관계 남용 → PK 상속 누적으로 과도한 조인/인덱스 비대.

4. 트랜잭션 (Transaction)

데이터를 조작하는 하나의 논리적 작업 단위. "전부 성공 아니면 전부 취소"로 묶이는 작업입니다.

💡 쉽게 말하면

쇼핑몰 결제 = '결제 성공' + '재고 차감'이 한 묶음. 재고 차감이 실패하면 결제도 롤백(취소)돼야 하죠. 중간 상태는 없습니다.

트랜잭션 4대 특성 — ACID (원·일·고·지)

원자성 (Atomicity)

전부 반영되거나 전부 취소. 중간은 없다.

일관성 (Consistency)

실행 전후 데이터가 모순 없이 일관된 상태 유지.

고립성 (Isolation)

실행 중 다른 트랜잭션이 끼어들지 못함.

지속성 (Durability)

완료(COMMIT)된 결과는 영구히 보존.

!

시험 포인트  "전부 아니면 전무" → 원자성. "다른 트랜잭션 간섭 차단" → 고립성. "완료 후 영구 보존" → 지속성. COMMIT/ROLLBACK은 TCL(ch3-3에서).

5. NULL 처리

값이 존재하지 않음(미지·미입력). 숫자 0이나 공백 문자('')와는 다릅니다.

상황NULL 처리
가로 연산 (수입 − 지출 등 컬럼끼리)하나라도 NULL이면 결과는 NULL
세로 연산 (SUM·AVG 등 집계)NULL을 제외하고 계산
NULL 비교 (COL > 5, COL = NULL)참이 아니라 UNKNOWN → 결과에서 빠짐
!

시험 포인트  ① NULL ≠ 0, NULL ≠ ''  ② NULL과의 사칙연산 결과 = NULL  ③ 집계함수(SUM/AVG/COUNT(컬럼))는 NULL 제외, 단 COUNT(*)는 NULL 포함해 전체 행을 셈  ④ NULL 비교는 IS NULL로만.

6. 분산 데이터베이스

데이터를 여러 물리적 장소(서버)에 나눠 저장하되, 사용자에게는 하나의 DB처럼 보이게 하는 방식입니다.

장점

지역 DB에서 빠르게 처리(응답↑), 장애 시 다른 서버가 대신(가용성↑), 확장 용이.

단점

여러 DB라 관리·보안·설계가 복잡, 데이터 일관성 유지가 어려움, 비용↑.

분산 투명성 6가지 — 사용자는 몰라도 된다

투명성의미 (사용자는 ~를 몰라도 된다)
분할(단편화)데이터가 여러 조각으로 나뉘어 저장된 것
위치데이터가 어느 서버(위치)에 있는지
지역사상지역 DBMS 이름·종류 같은 로컬 세부사항
중복(복제)같은 데이터가 여러 곳에 복제된 것
장애일부 서버 장애가 나도 정상 동작
병행여러 트랜잭션이 동시에 수행되는 것
!

시험 포인트  "어디 있는지 몰라도 된다" → 위치 투명성. "복제본이 여러 개인 걸 몰라도 된다" → 중복 투명성. 보기에서 없는 투명성(예: '보안 투명성')을 고르는 함정이 자주 나옵니다.

❓ 확인 퀴즈 · 분산 투명성
분산 데이터베이스의 투명성 유형이 아닌 것은?
정답 ③ 분산 투명성 6종 = 분할·위치·지역사상·중복·장애·병행. '보안 투명성'은 없는 용어입니다.
⏱️ 1과목 1-2 한눈에

정규화: 이상현상(삽입·갱신·삭제) 제거 → 1NF(원자값)·2NF(부분종속)·3NF(이행종속), 조회는 느려질 수 있음. 반정규화: 조회↑ 대신 정합성↓(중복·통계·이력·부분 / 백업은 아님). 트랜잭션 ACID. NULL은 집계서 제외·COUNT(*)만 포함. 분산 투명성 = 분할·위치·지역사상·중복·장애·병행.

SQL 활용

서브쿼리·뷰·집합 연산자·그룹 함수를 다룹니다. 계산 결과를 눈으로 보며 익히면 어렵지 않습니다. (조인·윈도우·계층형은 다음 '빈출 보충'에서 집중 정리)

1. 서브쿼리 (Subquery)

쿼리 안에 들어간 또 다른 쿼리. 바깥을 메인쿼리, 괄호 안을 서브쿼리라 합니다.

💡 쉽게 말하면

아기를 품은 엄마를 떠올리세요. 엄마(메인쿼리) 안에 아기(서브쿼리)가 있죠. 서브쿼리가 먼저 답을 구해 메인쿼리에 건네줍니다. 예) "평균 급여보다 많이 받는 사원" → 먼저 평균을 구하고(서브) 그보다 큰 사람을 고름(메인).

-- 평균 급여보다 많이 받는 사원 SELECT ENAME, SAL FROM EMP WHERE SAL > (SELECT AVG(SAL) FROM EMP); -- 서브쿼리가 평균(3250)을 반환

① 위치에 따른 분류

이름위치설명
스칼라 서브쿼리SELECT 절반드시 값 1개만 반환(컬럼 자리에)
인라인 뷰FROM 절쿼리 결과를 임시 테이블처럼 사용
중첩 서브쿼리WHERE / HAVING 절조건 비교에 사용

② 반환 형태에 따른 분류

종류반환함께 쓰는 연산자
단일 행1건 이하= > < >= <=
다중 행2건 이상IN · ANY · ALL · EXISTS (= 불가!)
다중 컬럼여러 컬럼IN 등 (컬럼 묶음 비교)
🔎 연관(상관) vs 비연관 서브쿼리

연관 서브쿼리: 서브쿼리가 메인쿼리의 컬럼을 참조(행마다 다시 실행). 주로 EXISTS와 함께. 비연관: 혼자 실행돼 값만 넘김. EXISTS는 "있기만 하면 참"이라 건수를 세지 않아 빠릅니다.

!

시험 포인트  ① 다중 행 서브쿼리에 =를 쓰면 에러 → IN 사용. ② ANY=하나라도 만족, ALL=모두 만족. ③ 스칼라 서브쿼리는 값이 딱 1개여야 함(2개 이상이면 에러). ④ 인라인 뷰 = FROM 절 서브쿼리.

2. 뷰 (View)

SELECT 문에 이름을 붙여 재사용하는 가상 테이블. 실제 데이터는 저장하지 않고 '정의'만 저장합니다.

CREATE VIEW V_영업사원 AS SELECT ENAME, SAL FROM EMP WHERE DEPT = '영업'; -- 이후엔 테이블처럼 사용 SELECT * FROM V_영업사원;

독립성

테이블 구조가 바뀌어도 뷰만 고치면 됨.

편리성

복잡한 쿼리를 뷰 이름 하나로 단순화.

보안성

민감 컬럼은 빼고 만들어 정보를 감춤.

!

함정  뷰의 장점은 독립성·편리성·보안성. '투명성'은 아님. 뷰는 자체 데이터·인덱스를 갖지 않고, 삽입·수정·삭제에 제약이 많습니다(집계·DISTINCT 포함 뷰 등은 수정 불가).

3. 집합 연산자

여러 SELECT 결과를 세로로 합치거나 빼는 연산입니다. 컬럼 개수·데이터 타입이 같아야 합니다.

연산자의미중복
UNION ALL합집합 (그대로 이어붙임)중복 유지 (정렬 안 함 → 빠름)
UNION합집합중복 제거 (+ 정렬 부하)
INTERSECT교집합 (공통)중복 제거
MINUS / EXCEPT차집합 (앞 − 뒤)중복 제거
★

핵심  ① 결과의 컬럼명(헤더)은 첫 번째 쿼리를 따름. ② ORDER BY는 맨 마지막에 한 번만. ③ MINUS=Oracle, EXCEPT=SQL Server(같은 차집합). ④ 중복 제거가 필요 없으면 UNION ALL이 빠름.

4. 그룹 함수 — ROLLUP · CUBE · GROUPING SETS

소계(소그룹별 합)와 총계를 한 번에 구하는 함수입니다. 2과목에서 제일 까다롭지만, "무엇으로 그룹핑되는가"만 비교하면 됩니다.

함수그룹핑 결과 (부서 A, 직급 B 기준)
GROUP BY A, B①(A,B)별  — 소계·총계 없음
ROLLUP(A, B)①(A,B)별 ②A별 ③총계  (한 방향 소계)
CUBE(A, B)①(A,B)별 ②A별 ③B별 ④총계  (모든 조합)
GROUPING SETS(A, B)①A별 ②B별  (지정한 것만, 총계 없음)
💡 핵심 직관

ROLLUP = 계단식 소계(왼→오 한 방향). CUBE = 가능한 모든 조합의 소계(다차원, 집계 건수 최다). GROUPING SETS = 내가 지정한 묶음만 개별 집계. 괄호로 묶은 (A,B)는 '한 덩어리'로 취급됩니다.

예) 부서·직급별 급여합을 ROLLUP으로 구하면 👇 (소계 행이 자동으로 추가됨)

부서직급급여합
영업사원3000
영업대리4000
영업(소계)7000
(전체)(총계)7000
!

시험 포인트  "결합 가능한 모든 집계" = CUBE. ROLLUP((A,B), C) → (A,B,C)별 → (A,B)별 → 총계. 소계 행의 NULL 자리는 GROUPING() 함수(1이면 소계)로 구분합니다.

❓ 확인 퀴즈 · 집합 연산자
차집합과 같은 역할을 하는 집합 연산자는?
정답 ② 차집합 = MINUS(Oracle) / EXCEPT(SQL Server). 교집합은 INTERSECT, 합집합은 UNION.
❓ 확인 퀴즈 · 그룹 함수
A, B 두 컬럼의 모든 조합(A·B·AB·총계)을 집계하는 함수는?
정답 ③ 모든 조합(다차원) 집계는 CUBE. ROLLUP은 한 방향 소계, GROUPING SETS는 지정한 것만.
⏱️ 2과목 2-2 한눈에

서브쿼리 위치 = 스칼라(SELECT)·인라인뷰(FROM)·중첩(WHERE). 다중행엔 IN/ANY/ALL/EXISTS(=불가). 뷰=가상 테이블(독립·편리·보안). 집합: UNION(중복제거)·UNION ALL(유지)·INTERSECT·MINUS. 그룹: ROLLUP(한방향)·CUBE(모든조합)·GROUPING SETS(지정).

2과목 · 2-3 관리 구문

관리 구문

SQL 명령어를 4종류로 나눠 익힙니다. DML·TCL·DDL·DCL — 어느 명령어가 어디 속하는지가 단골 출제입니다. 제약조건·CREATE 실전도 함께 봅니다.

0. 명령어 4대 분류 — 먼저 이 표부터

분류풀이명령어COMMIT
DML데이터 조작어SELECT, INSERT, UPDATE, DELETE, MERGE필요(수동)
TCL트랜잭션 제어어COMMIT, ROLLBACK, SAVEPOINT—
DDL데이터 정의어CREATE, ALTER, DROP, RENAME, TRUNCATE자동(Auto)
DCL데이터 제어어GRANT, REVOKE자동
★

암기팁  헷갈리는 둘: COMMIT/ROLLBACK은 TCL(DDL 아님!), TRUNCATE는 DDL(DML 아님!). DDL·DCL은 실행 즉시 자동 COMMIT이라 ROLLBACK이 안 됩니다.

1. DML — 데이터 조작어

-- 입력 INSERT INTO EMP (EMPNO, ENAME, SAL) VALUES (5, '한지민', 2800); -- 수정 (WHERE 없으면 전체 행!) UPDATE EMP SET SAL = SAL * 1.1 WHERE DEPT = '영업'; -- 삭제 (WHERE 없으면 전체 행!) DELETE FROM EMP WHERE EMPNO = 5;
명령어설명주의
INSERT행 입력PK·NOT NULL 컬럼엔 NULL 불가
UPDATE행 수정WHERE 없으면 전체 수정
DELETE행 삭제WHERE 없으면 전체 삭제, COMMIT 전 ROLLBACK 가능
MERGE입력+수정 한 번에ON 조건으로 MATCHED/NOT MATCHED 분기(동기화)
🔎 DELETE vs TRUNCATE vs DROP — 자주 나옴

DELETE: 행만 삭제, ROLLBACK 가능, 로그 남김, 구조 유지. TRUNCATE: 전체 행 삭제 + 저장공간 초기화, ROLLBACK 불가(DDL), 매우 빠름, 구조 유지. DROP: 테이블 구조까지 통째 삭제. "미련 남기는 DELETE, 깔끔히 비우는 TRUNCATE, 집까지 허무는 DROP"으로 기억!

!

시험 포인트  1억 건을 빠르게 비우고 테이블은 유지 → TRUNCATE. 일부만 지우고 되돌릴 수 있어야 함 → DELETE. Oracle은 DML 후 COMMIT해야 반영(SQL Server는 기본 AUTO COMMIT).

2. TCL — 트랜잭션 제어어

명령어설명
COMMIT변경 내용을 확정·반영. 해야 최종 저장됨
ROLLBACK변경 내용을 취소하고 이전 값으로 복구
SAVEPOINT 이름중간 지점 저장 → ROLLBACK TO 이름으로 일부만 되돌림
★

핵심  COMMIT 전까지 변경은 메모리에만 있어 다른 사용자는 못 봄. 오래 COMMIT/ROLLBACK 안 하면 LOCK이 걸려 남이 그 행을 수정하지 못합니다.

3. DDL — 데이터 정의어 + 제약조건

데이터 유형 — CHAR vs VARCHAR

CHAR (고정 길이)

정한 크기를 항상 다 차지. 'IU'를 CHAR(10)에 넣으면 10byte(뒤는 공백). 비교 시 공백 무시 → 'IU' = 'IU  '.

VARCHAR (가변 길이)

실제 크기만 사용. 'IU'는 2byte. 비교 시 공백도 문자 → 'IU' ≠ 'IU  '.

CREATE TABLE — 제약조건과 함께

CREATE TABLE ORDERS ( ORD_ID NUMBER PRIMARY KEY, -- 유일 + NOT NULL MEMBER_ID VARCHAR2(10) NOT NULL, -- 빈 값 금지 QTY NUMBER DEFAULT 1 CHECK (QTY > 0), -- 기본값·값 범위 CONSTRAINT FK_MEM FOREIGN KEY (MEMBER_ID) REFERENCES MEMBER (MEMBER_ID) -- 참조 무결성 );
제약조건의미
PRIMARY KEY기본키 = 유일성 + NOT NULL (테이블당 1개)
FOREIGN KEY다른 테이블 PK 참조 → 참조 무결성
UNIQUE중복 금지 (단, NULL은 허용)
NOT NULL빈 값 금지
CHECK값의 범위·조건 지정 (예: 나이 ≥ 0)
DEFAULT값 생략 시 들어갈 기본값

주요 DDL 명령어

명령어설명
ALTER ... ADD컬럼/제약조건 추가 (컬럼은 항상 맨 끝에)
ALTER ... MODIFY데이터유형·DEFAULT·NOT NULL 변경
ALTER ... DROP COLUMN컬럼 삭제(복구 불가)
ALTER ... RENAME COLUMN컬럼명 변경
DROP TABLE테이블 삭제(참조 있으면 CASCADE CONSTRAINT)
🔎 CTAS (테이블 복사 생성)

CREATE TABLE 새테이블 AS SELECT * FROM 원본 → 구조+데이터 복사. 단 NOT NULL만 복사되고 PK·UNIQUE·CHECK·FK는 복사되지 않으니 필요하면 ALTER로 다시 추가합니다.

!

시험 포인트  컬럼 유형·DEFAULT·NOT NULL 변경 → MODIFY. 컬럼 추가 → ADD. UNIQUE는 NULL 허용(PK는 불가). CASCADE는 Oracle에 있고 SQL Server엔 없음.

4. DCL — 데이터 제어어 (권한)

💡 쉽게 말하면

DB를 '집'이라 하면 USER는 '룸메이트'. 사람을 들이고(CREATE USER + 비밀번호), 집을 쓸 권한을 줘야(GRANT) 방에 들어갈 수 있어요. 권한 회수는 REVOKE.

GRANT SELECT, INSERT ON EMP TO PERPEAR; -- 권한 부여 REVOKE INSERT ON EMP FROM PERPEAR; -- 권한 회수
명령어설명
GRANT 권한 ON 객체 TO 사용자권한 부여
REVOKE 권한 ON 객체 FROM 사용자권한 회수
ROLE여러 권한을 하나로 묶은 세트(빅맥세트처럼). ROLE을 사용자에게 GRANT
❓ 확인 퀴즈 · 명령어 분류
다음 중 DDL이 아닌 것은?
정답 ② COMMIT은 TCL입니다. DDL = CREATE·ALTER·DROP·RENAME·TRUNCATE.
❓ 확인 퀴즈 · TRUNCATE
TRUNCATE에 대한 설명으로 올바른 것은?
정답 ① TRUNCATE는 DDL — 전체 행+공간 초기화, 구조 유지, 자동 COMMIT이라 ROLLBACK 불가. 구조까지 지우는 건 DROP.
⏱️ 2과목 2-3 한눈에

DML(I·U·D·MERGE, 수동 COMMIT) · TCL(COMMIT·ROLLBACK·SAVEPOINT) · DDL(CREATE·ALTER·DROP·RENAME·TRUNCATE, 자동COMMIT) · DCL(GRANT·REVOKE). 제약 6종: PK·FK·UNIQUE(NULL허용)·NOT NULL·CHECK·DEFAULT. ALTER: 추가=ADD, 유형변경=MODIFY.

3. 계층형 쿼리 (Hierarchical Query)

부모-자식처럼 계층 구조(조직도, 카테고리, 사원-상사)를 펼쳐 조회합니다. Oracle의 CONNECT BY를 씁니다.

SELECT LEVEL, 이름 FROM EMP START WITH 상사ID IS NULL -- ① 최상위(사장)에서 시작 CONNECT BY PRIOR 사원ID = 상사ID; -- ② 부모의 사원ID = 자식의 상사ID (순방향)
키워드의미

계층 전개 — START WITH 루트에서 CONNECT BY로 아래로 (LEVEL=깊이)

🔎 순방향 vs 역방향

PRIOR 사원ID = 상사ID → 위에서 아래로(사장→사원) 순방향 전개. 좌우를 바꾼 PRIOR 상사ID = 사원ID → 아래에서 위로(사원→사장) 역방향 전개. PRIOR가 붙은 쪽이 '부모'라고 기억하세요.

4. 윈도우 함수 (Window Function) 빈출

GROUP BY처럼 묶지만 행을 줄이지 않고, 각 행 옆에 순위·누적합·이전값 같은 계산을 붙입니다. 핵심은 OVER (PARTITION BY ... ORDER BY ...).

SELECT 이름, 부서, 급여, RANK() OVER (PARTITION BY 부서 ORDER BY 급여 DESC) AS 부서내순위 FROM EMP;

순위 함수 — RANK vs DENSE_RANK vs ROW_NUMBER

같은 급여(공동 1위)가 있을 때 차이가 핵심입니다. 👇 (급여순 정렬)

💡 한 줄 정리

RANK = 공동 순위 후 건너뜀(1,1,3). DENSE_RANK = 안 건너뜀(1,1,2). ROW_NUMBER = 무조건 1,2,3(동점도 구분). 올림픽 메달식이 RANK입니다.

함수기능
SUM() OVER (ORDER BY ...)누적 합계(행이 쌓일수록 누적)

시험 포인트  RANK vs DENSE_RANK(건너뛰기 유무)가 최다 출제. PARTITION BY=그룹 나눔, ORDER BY=그룹 내 정렬. 비율 함수(CUME_DIST·PERCENT_RANK·RATIO_TO_REPORT)는 0~1 범위.

❓ 확인 퀴즈 · 순위 함수
공동 1위가 둘일 때 다음 순위를 '2'로 매기는(건너뛰지 않는) 함수는?
정답 ② DENSE_RANK는 1,1,2로 건너뛰지 않음. RANK는 1,1,3으로 건너뜀, ROW_NUMBER는 동점도 1,2,3.

5. 실행 순서 · 연산자 우선순위

SQL 실행 순서

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY

연산자 우선순위

산술 → 연결(||) → 비교 → IN·LIKE·BETWEEN·IS NULL → NOT → AND → OR

★

암기팁  실행 순서 = "프 → 웨 → 그 → 하 → 셀 → 오". SELECT는 거의 마지막, ORDER BY가 진짜 마지막. 작성 순서와 실행 순서가 다른 것이 함정(그래서 WHERE에선 SELECT 별칭을 못 씀).

❓ 확인 퀴즈 · 실행 순서
SQL문의 실행 순서로 올바른 것은?
정답 ① FROM(테이블) → WHERE(행 필터) → GROUP BY(묶기) → HAVING(그룹 필터) → SELECT(인출) → ORDER BY(정렬).

6. GROUP BY · HAVING · 집계함수

데이터를 묶어 합계·평균·개수를 구합니다.

SELECT 부서, COUNT(*) AS 인원, AVG(급여) AS 평균 FROM EMP WHERE 급여 > 2000 -- ① 묶기 전 행 필터 GROUP BY 부서 -- ② 부서별로 묶기 HAVING COUNT(*) >= 2; -- ③ 묶은 뒤 그룹 필터
!

시험 포인트  ① WHERE=그룹 전, HAVING=그룹 후 필터. ② SELECT에 집계함수와 함께 쓴 일반 컬럼은 반드시 GROUP BY에 포함. ③ 집계함수(SUM·AVG·COUNT(컬럼))는 NULL 제외, COUNT(*)만 NULL 포함해 전체 행을 셈.

7. CASE · DECODE

SELECT 이름, CASE WHEN 급여 >= 4000 THEN '고급' WHEN 급여 >= 3000 THEN '중급' ELSE '초급' END AS 등급 FROM EMP;
구문설명
CASE WHEN 조건 THEN … ELSE … ENDIF-THEN-ELSE 논리. 범위 조건 가능(≥, BETWEEN 등)
DECODE(컬럼, A, 결과1, 기본값)Oracle 전용. = 비교만 가능(범위 불가)
!

시험 포인트  ① CASE col WHEN NULL THEN…은 NULL을 못 잡음 → 반드시 WHEN col IS NULL. ② DECODE는 등호(=) 비교만, 범위 비교는 CASE로. ③ CASE는 위에서부터 먼저 맞는 조건에서 멈춤.

8. TOP-N 쿼리 (상위 N건)

방식문법
Oracle ROWNUMWHERE ROWNUM <= 5 (정렬 필요 시 인라인 뷰로 ORDER BY 먼저)
ANSI FETCHORDER BY 급여 DESC FETCH FIRST 5 ROWS ONLY
OFFSET … FETCHOFFSET 10 ROWS FETCH NEXT 5 ROWS ONLY (11~15위)
SQL Server TOP / MySQL LIMITSELECT TOP 5 … / … LIMIT 5
!

함정 주의  WHERE ROWNUM <= 5 ORDER BY ...는 정렬 전에 5건을 잘라버려 원하는 상위 5건이 아닐 수 있음. 반드시 정렬된 인라인 뷰를 먼저 만든 뒤 ROWNUM을 거세요.

❓ 확인 퀴즈 · TOP-N
정렬된 상위 5건을 올바르게 조회하는 Oracle 방식은?
정답 ② ROWNUM은 정렬 전에 매겨지므로 정렬된 인라인 뷰를 먼저 만든 뒤 ROWNUM을 걸어야 진짜 상위 5건. (TOP=SQL Server, LIMIT=MySQL)

9. PIVOT / UNPIVOT · 정규표현식

PIVOT

행 → 열로 회전. 세로로 쌓인 데이터를 가로 교차표로. (월별 매출을 '1월·2월·3월' 컬럼으로)

UNPIVOT

열 → 행으로 되돌림. 가로로 펼친 컬럼을 세로 데이터로.

💡 쉽게 말하면

엑셀 '피벗 테이블'과 같습니다. PIVOT=세로 목록을 가로 요약표로, UNPIVOT=그 반대. 방향만 기억하면 됩니다.

정규식 기호/함수의미
^ / $문자열의 시작 / 끝
. / |임의의 한 문자 / OR
[ ] / [^ ]안의 문자 중 하나 / 제외한 하나
REGEXP_LIKE / REGEXP_SUBSTR패턴 일치 여부(조건) / 패턴 부분 추출
!

시험 포인트  ^=시작, $=끝이 단골. [ ]=하나와 일치, [^ ]=제외. 자주는 아니지만 기호 뜻만 알면 풀립니다.

⏱️ 빈출 보충 한눈에

JOIN: INNER(교집합)·OUTER(한쪽 다)·CROSS(곱), ON 빠지면 CROSS, Oracle (+)는 반대쪽. 계층형=START WITH·CONNECT BY·PRIOR·LEVEL. 윈도우: RANK(건너뜀)·DENSE_RANK(안건너뜀)·ROW_NUMBER. 실행순서=프웨그하셀오. CASE는 범위 OK·DECODE는 =만. TOP-N은 정렬 후 ROWNUM.
