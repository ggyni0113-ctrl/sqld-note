# 데이터 모델링의 이해

현실의 업무를 데이터베이스로 옮기는 첫 단계입니다. 이 파트의 핵심은 **용어 구분** — 데이터 모델·엔터티·속성·관계·식별자의 뜻을 분명히 잡는 것입니다.

------------------------------------------------------------------------

### 1. 데이터 모델의 이해

> **정의** 데이터 모델이란 현실 세계의 복잡한 정보를 컴퓨터에 저장하기 위해 그린 설계 도면 이다.  
> ex) 회원·상품·주문 같은 정보를 어떻게 저장하고 연결할지 데이터베이스 구조로 시각화하는 과정.

> \*\*💡 쉽게 말하면\*\* 데이터 모델링은 현실을 지도로 그리는 일 이에요. 실제 도시엔 건물·사람·차가 가득하지만 지도엔 길과 주요 건물만 간단히 그리죠. 똑같이, 복잡한 회사 업무에서 "저장·관리할 정보"만 골라 깔끔한 그림으로 옮기는 게 데이터 모델링입니다.

#### 데이터 모델링의 단계 — 개념 → 논리 → 물리 ('개-논-물')

추상적인 개념에서 구체적인 구현 단계로 진행됩니다. 각 단계의 산출물이 자주 출제됩니다.

**1. 개념적 데이터 모델링 (Conceptual)** — 데이터 요구사항을 분석해 핵심 엔터티와 그 관계를 나타내는 ERD 를 생성. 전사적 관점, 추상화 수준이 가장 높음.

**2. 논리적 데이터 모델링 (Logical)** — 속성·PK·FK를 채우고 정규화 수행. DBMS와 무관. 모델링의 최종 완료 상태.

**3. 물리적 데이터 모델링 (Physical)** — 실제 DBMS에 맞춰 CREATE TABLE + 인덱스·파티션·자료형 명시. 성능·보안·가용성 고려.

**4. 데이터베이스 운영** — 테이블에 데이터가 차곡차곡 쌓인 상태. 사용자가 SQL로 조회·입력·수정.

> \*\*🏠 집 짓기로 비유\*\* 개념적 = '방3·거실1' 손스케치 → 논리적 = 치수·배관까지 그린 설계도면 → 물리적 = 벽돌로 실제 시공. 뒤로 갈수록 구체적·기술적이 됩니다.

| 단계                 | 결과물                              | 비유               |
|----------------------|-------------------------------------|--------------------|
| **1. 개념적 모델링** | 핵심 엔터티·관계 ERD (큰 그림)      | 손으로 그린 스케치 |
| **2. 논리적 모델링** | 속성·키 상세 ERD + 정규화           | 정식 건축 도면     |
| **3. 물리적 모델링** | DBMS별 CREATE TABLE + 인덱스·파티션 | 시공 계획서        |
| → 운영               | 데이터가 쌓인 실제 데이터베이스     | 입주 완료된 건물   |

#### SQL 실전 — 모델이 곧 테이블이 된다

논리 모델의 PK는 물리 모델에서 **PRIMARY KEY 제약(식별자)**이 됩니다.

    -- 논리 모델의 '회원/상품/주문' 엔터티 → 물리 모델의 테이블
    CREATE TABLE MEMBER (
        MEMBER_ID  VARCHAR2(10) PRIMARY KEY,   -- 식별자
        NAME       VARCHAR2(50) NOT NULL,
        PHONE      VARCHAR2(20)
    );
    CREATE TABLE ORDERS (
        ORDER_ID   NUMBER PRIMARY KEY,
        MEMBER_ID  VARCHAR2(10) REFERENCES MEMBER(MEMBER_ID),  -- 관계=FK
        ORD_DATE   DATE DEFAULT SYSDATE
    );
    CREATE INDEX IDX_ORDERS_MEMBER ON ORDERS(MEMBER_ID);  -- 성능용 인덱스(물리)

#### 데이터 모델링의 3가지 관점

| 관점              | 내용                                 | 질문 / 분석                                         |
|-------------------|--------------------------------------|-----------------------------------------------------|
| **데이터 관점**   | 업무가 관리하는 데이터(엔터티·속성)  | 무엇을(What) 저장하지 · 구조(정적) 분석             |
| **프로세스 관점** | 업무가 실제 하는 일(또는 해야 할 일) | 어떻게(How) 처리하지 · 시나리오(동적) 분석          |
| **상관관계 관점** | 프로세스가 데이터에 미치는 영향      | 언제(When) 어떤 데이터가 변하지 · **CRUD 매트릭스** |

#### 좋은 데이터 모델의 요소 (6가지)

| 요소                | 의미                                       |
|---------------------|--------------------------------------------|
| **① 완전성**        | 업무에 필요한 데이터를 빠짐없이 담았는가   |
| **② 중복 배제**     | 같은 데이터가 여러 곳에 흩어져 있지 않은가 |
| **③ 업무 규칙**     | 회사의 규칙이 모델에 녹아 있는가           |
| **④ 데이터 재사용** | 다른 업무에서도 활용할 수 있는가           |
| **⑤ 의사소통**      | 보는 사람마다 같은 의미로 읽히는가         |
| **⑥ 통합성**        | 같은 데이터는 한 곳에만 정의되어 있는가    |

#### 3층 스키마 (ANSI/SPARC)

같은 데이터베이스를 세 관점에서 본 모습. 관점을 나눠 **데이터 독립성**을 확보합니다.

> \*\*🎬 쉽게 말하면\*\* 영화관에서 관객 은 스크린만(외부), 기획자 는 전체 구성을(개념), 영사기사 는 필름 작동을(내부) 봅니다. 관점을 나눠두면 한쪽이 바뀌어도 다른 쪽이 안 흔들립니다.

| 스키마                | 관점 / 개수 / 담당                      | 내용                                                              |
|-----------------------|-----------------------------------------|-------------------------------------------------------------------|
| **외부 (External)**   | 사용자·응용 / 여러 개 / 사용자·개발자   | 각 사용자·앱이 보는 화면. SQL의 **VIEW** 또는 응용의 가공 데이터. |
| **개념 (Conceptual)** | 설계자 / 1개 / DA(Data Architect)       | 조직 전체가 공유하는 통합 ERD. 모든 화면의 원본이 되는 설계도.    |
| **내부 (Internal)**   | 물리 저장 / 1개 / DBA(DB Administrator) | 디스크 위 실제 저장 구조. 데이터 파일·인덱스·파티션·캐시.         |

    -- 외부 스키마(VIEW) — 응용 프로그램이 보는 화면
    CREATE VIEW V_MY_ORDER AS
    SELECT O.ORDER_ID, O.ORD_DATE, M.NAME
      FROM ORDERS O JOIN MEMBER M ON M.MEMBER_ID = O.MEMBER_ID;
    -- 개념 스키마(MEMBER+ORDERS 두 테이블)는 그대로지만, VIEW를 통해
    -- 외부 스키마는 "주문번호·날짜·이름" 한 화면처럼 보인다.

#### 데이터 독립성 2가지

| 종류              | 의미                                                               |
|-------------------|--------------------------------------------------------------------|
| **논리적 독립성** | 개념 스키마가 변경돼도 외부 스키마(응용)는 영향 없음 (개념 ↔ 외부) |
| **물리적 독립성** | 내부 스키마가 변경돼도 개념·외부 스키마는 영향 없음 (내부 ↔ 개념)  |

#### Before & After — 모델링이 없을 때 vs 있을 때

김철수가 사과·배·포도를 여러 번 주문한 상황. 한 테이블에 다 욱여넣은 형태와, 고객·주문을 분리한 형태를 비교합니다.

**BEFORE · 모델링 없이**

고객 정보 중복 + 상품 칸이 모자라면 못 담음

→

**AFTER · 엔터티 분리**

| CUSTOMER                 |
|--------------------------|
| C001 · 김철수 · 010-1111 |

| ORDER           |
|-----------------|

#### 시험 포인트

| 출제 포인트       | 시험에서 묻는 방식                                                                                    |
|-------------------|-------------------------------------------------------------------------------------------------------|
| 모델링 3가지 관점 | 데이터(What)·프로세스(How)·상관(Interaction) 중 해당 없는 것 고르기. "기술 관점"이 오답으로 자주 등장 |
| 모델링 3단계      | 개념 → 논리 → 물리 순서와 산출물. 정규화는 논리 단계에서 수행                                         |
| 3층 스키마        | 외부(여러 개·VIEW)·개념(1개·전사 ERD)·내부(1개·저장 구조)를 산출물과 짝짓기                           |
| 데이터 독립성     | 논리적=개념↔외부, 물리적=내부↔개념. 어느 스키마가 바뀌었는지로 구분                                   |
| 모델링 유의점     | 중복(Duplication)·비유연성(Inflexibility)·비일관성(Inconsistency) 세 가지의 정의 구분                 |

#### 자주 틀리는 함정

- **함정:** 모델링 관점에 "기술 관점(Technical)"이 포함된다. **→ 바로잡기:** 데이터·프로세스·상관 세 가지뿐이다. 기술 관점은 존재하지 않는 선택지.
- **함정:** 인덱스·파티션을 바꿨으니 논리적 독립성이다. **→ 바로잡기:** 저장 구조 변경은 내부 스키마의 일 → 물리적 독립성 .

⏱ 30초 정리

3단계는 **개-논-물**(정규화는 논리). 3층은 **외-개-내**(개념·내부는 각 1개, 외부만 여러 개). 유의점 = 중복·비유연성·비일관성. 독립성 = 논리적(개념↔외부)·물리적(내부↔개념).

### 2. ERD 작성 절차 (보충)

ERD는 엔터티와 관계를 그리는 표준 방법(1976년 피터 첸 고안). 작성은 **6단계 순서**로 진행되며 이 순서가 자주 출제됩니다.

**1. 엔터티를 도출하고 그린다** — 업무에서 관리할 집합(덩어리)을 찾습니다.

**2. 엔터티를 배치한다** — 중요한 엔터티를 왼쪽 상단 에 배치합니다.

**3. 엔터티 간 관계를 설정한다** — 연결되는 엔터티끼리 선을 긋습니다.

**4. 관계명을 서술한다** — 어떤 행위/존재가 있는지 이름을 붙입니다.

**5. 관계 참여도를 표현한다** — 서로 몇 개씩 참여하는지(예: 고객1 : 계좌N).

**6. 관계의 필수 여부를 표현한다** — 반드시 있어야 하는 관계인지 표시합니다.

> 암기팁 "누가 있나(1·2) → 어떻게 잇나(3) → 이름(4) → 몇 개(5) → 필수(6)". 관계 3종(관계명→참여도→필수)은 항상 뒤쪽 에 옵니다.

**❓ 확인 퀴즈 · ERD 절차**

ERD 작성 절차로 올바른 것은? (ㄱ엔터티도출 · ㄴ배치 · ㄷ관계설정 · ㄹ관계명 · ㅁ참여도 · ㅂ필수여부)

1.  ㄱ → ㄴ → ㄷ → ㄹ → ㅁ → ㅂ
2.  ㄱ → ㄴ → ㄷ → ㄹ → ㅂ → ㅁ
3.  ㄴ → ㄱ → ㄷ → ㄹ → ㅁ → ㅂ
4.  ㄱ → ㄷ → ㄴ → ㄹ → ㅁ → ㅂ

> 정답 ① 도출→배치→관계설정→관계명→참여도→필수여부.

### 3. 엔터티 (Entity)

> **정의** 엔터티란 업무에서 관리해야 할 정보의 덩어리(명사) 다. 실제 테이블의 후보가 된다.  
> ex) 쇼핑몰이라면 회원·상품·주문·배송 같은 명사 하나하나가 엔터티. 각 엔터티의 개별 사례('김철수 회원')를 인스턴스(한 행) 라 한다.

> \*\*📦 쉽게 말하면\*\* 엔터티는 엑셀 시트 한 장의 제목 ('회원' 시트, '주문' 시트)이에요. 표 자체가 엔터티(MEMBER), 헤더가 속성, 각 행이 인스턴스입니다.

#### 엔터티의 구성 — 엔터티 / 속성 / 인스턴스

| MEMBER_ID | NAME   | PHONE    | JOIN_DATE  | ← 속성(컬럼)   |
|-----------|--------|----------|------------|----------------|
| C001      | 김철수 | 010-1111 | 2026-01-15 | ← 인스턴스(행) |
| C002      | 이영희 | 010-2222 | 2026-02-08 | ← 인스턴스(행) |

*표 자체가 엔터티(MEMBER), 헤더가 속성, 각 행이 인스턴스.*

#### 엔터티의 5가지 특징 — '업·식·인·속·관'

**업 — 업무에 필요** — 관리할 가치가 있는 정보여야 한다.

**식 — 식별 가능** — 식별자로 유일하게 구분된다.

**인 — 인스턴스 ≥ 2** — 2개 이상의 행이 존재해야 한다.

**속 — 속성 ≥ 2** — 2개 이상의 속성을 가진다.

**관 — 관계 보유** — 다른 엔터티와 최소 1개 이상의 관계를 가진다.

#### 엔터티의 분류

① 유무형에 따른 분류

**유형 엔터티** — 물리적으로 존재 — 상품·사원·매장

**개념 엔터티** — 개념적으로만 존재 — 부서·조직·학과

**사건 엔터티** — 행위로 발생 — 주문·결제·출입기록

② 발생 시점에 따른 분류

**기본(키) 엔터티** — 다른 엔터티 없이도 성립 — 사원·부서·고객

**중심 엔터티** — 기본에서 발생 — 주문·계약·매출

**행위 엔터티** — 2개 이상 엔터티의 관계에서 발생 — 주문상세·출고·입출금

#### SQL 실전 — 엔터티는 테이블이 된다

    CREATE TABLE MEMBER (
        MEMBER_ID    VARCHAR2(10) PRIMARY KEY,  -- 식별자
        NAME         VARCHAR2(50),
        PHONE        VARCHAR2(20),
        JOIN_DATE    DATE
    );
    -- 인스턴스(행) 입력
    INSERT INTO MEMBER VALUES('M01', '김철수', '010-1111', DATE '2026-01-15');
    INSERT INTO MEMBER VALUES('M02', '이영희', '010-2222', DATE '2026-02-08');
    -- 조회: 두 인스턴스에서 두 속성만 골라 보여준다
    SELECT MEMBER_ID, NAME FROM MEMBER;

*엔터티(설계 단계) → 테이블(SQL 단계) → 행(인스턴스)으로 단계가 매핑됩니다.*

→

**AFTER · 회원·상품·주문 분리**

#### 시험 포인트

| 출제 포인트           | 시험에서 묻는 방식                                                                      |
|-----------------------|-----------------------------------------------------------------------------------------|
| 엔터티의 5가지 특징   | 업무 필요·유일 식별·인스턴스 2개 이상·속성 2개 이상·관계 1개 이상. **개수 조건이 함정** |
| 유무형에 따른 분류    | 유형(형태 있음)·개념(추상적)·사건(업무 수행으로 발생)                                   |
| 발생 시점에 따른 분류 | 기본/키(스스로 생성)·중심(기본에서 발생)·행위(둘 이상에서 발생). 해당 없는 것 찾기      |
| 엔터티 명명 규칙      | 현업 용어·약어 지양·단수 명사·전체에서 유일한 이름                                      |
| 엔터티 vs 인스턴스    | 엔터티는 집합, 인스턴스는 그 집합의 한 건(테이블의 한 행)                               |

#### 자주 틀리는 함정

- **함정:** 속성이 하나뿐인 엔터티도 있을 수 있다. **→ 바로잡기:** 엔터티는 속성 2개 이상·인스턴스 2건 이상이어야 한다.
- **함정:** 프로젝트·주문처럼 업무에 늘 있으면 기본 엔터티다. **→ 바로잡기:** 다른 엔터티로부터 발생하는지가 기준. 주문은 고객·상품에서 발생 → 중심 엔터티 .

⏱ 30초 정리

특징 5개 = **업·식·인·속·관**(인스턴스·속성은 2개 이상). 유무형 = 유형·개념·사건. 발생시점 = 기본·중심·행위.

### 4. 속성 (Attribute)

> **정의** 속성이란 엔터티가 가지는 세부 정보 항목, 곧 컬럼 이다. 엔터티를 설명하는 가장 작은 단위다.  
> ex) 명함 한 장에서 명함 자체는 엔터티(사람), 이름·전화번호·이메일 같은 각 항목이 속성. 이름은 더 이상 쪼개지지 않는 최소 단위.

> \*\*🔎 엔터티 / 인스턴스 / 속성 / 속성값\*\* 회원 테이블에서 각 행 = 인스턴스 , 각 컬럼 = 속성 , 각 칸 = 속성값(Value) . 예: (M01, 김철수, 010-1111)에서 '010-1111'이 속성값.

#### 속성의 3가지 분류 기준

**① 특성 · 기본 / 설계 / 파생**

데이터가 어디서 왔는가

**② 분해 · 단순(원자) / 복합**

더 쪼갤 수 있는가

**③ 값 개수 · 단일값 / 다중값**

한 인스턴스에 몇 개?

| 기준          | 종류            | 의미 (예)                                                        |
|---------------|-----------------|------------------------------------------------------------------|
| **① 특성**    | 기본 속성       | 업무에서 직접 추출된 본래 속성 (이름, 전화번호, 주소)            |
|               | 설계 속성       | 설계 과정에서 새로 만든 속성 (회원ID, 상품코드)                  |
|               | 파생 속성       | 다른 속성에서 계산되어 나온 속성 (총주문금액 = 수량 × 단가)      |
| **② 분해**    | 단순(원자) 속성 | 더 이상 분해 불가 (이름, 나이)                                   |
|               | 복합 속성       | 여러 의미가 합쳐진 형태 — 분해 저장 시 활용도↑ (주소 = 시+구+동) |
| **③ 값 개수** | 단일값 속성     | 하나만 가짐 (주민번호)                                           |
|               | 다중값 속성     | 여러 개 가능 → **별도 엔터티로 분리** (전화번호: 집·휴대폰)      |

> 시험 단골 "주민번호로부터 구한 나이"는 파생 속성 . 복합 속성(1-1-4)과 복합식별자(1-1-6)는 다른 개념 — 복합 속성은 한 속성을 여러 의미로 쪼갬, 복합식별자는 여러 속성을 묶어 PK로 씀.

#### 구성에 따른 분류 & 명명 규칙

속성은 역할에 따라 **PK 속성·FK 속성·일반 속성**으로도 나뉩니다.

- 코드가 아닌 **현업 용어**로 명명 ('회원_등록일' O, 'regdt' X).
- **명사형**으로 ('주문수량' O, '주문은얼마인가' 서술식 X).
- 약어 자제 ('qty'보다 '수량'). 전체 모델에서 유일한 이름.

> **도메인(Domain)** 속성이 가질 수 있는 값의 종류·범위·제약. 데이터 타입 + 크기 + 허용값(제약) 세 가지가 모두 포함되며, NULL 허용 여부도 도메인의 일부.  
> 성별 = CHAR(1) / {'M','F'}만 허용 · 나이 = NUMBER(3) / 0~150 · 이메일 = VARCHAR2(100) / @ 포함

#### SQL 실전 — 파생 속성 & 도메인(CHECK)

    CREATE TABLE MEMBER (
        MEMBER_ID  VARCHAR2(10),   -- 설계 속성
        NAME       VARCHAR2(50),   -- 기본 속성
        BIRTH      DATE,           -- 기본 속성
        AGE        NUMBER GENERATED ALWAYS AS -- 파생 속성(자동 계산)
                   (TRUNC(MONTHS_BETWEEN(SYSDATE, BIRTH)/12)) VIRTUAL
    );
    -- 도메인을 제약조건(CHECK)으로 표현
    CREATE TABLE SURVEY (
        GENDER  CHAR(1) CHECK(GENDER IN('M','F')),      -- 허용값 도메인
        AGE     NUMBER(3) CHECK(AGE BETWEEN 0 AND 150) NOT NULL
    );

#### Before & After — 다중값 속성의 분리

**BEFORE · 다중값을 한 칸에**

| ID  | NAME   | PHONE                 |
|-----|--------|-----------------------|
| M01 | 김철수 | 010-1111, 02-333-4444 |

검색·변경 어려움 · 1NF 위반

→

**AFTER · 별도 엔터티 분리**

| MEMBER       |
|--------------|
| M01 · 김철수 |

| ID  | TYPE   | PHONE       |
|-----|--------|-------------|
| M01 | 휴대폰 | 010-1111    |
| M01 | 집     | 02-333-4444 |

#### 시험 포인트

| 출제 포인트     | 시험에서 묻는 방식                                                   |
|-----------------|----------------------------------------------------------------------|
| 속성 분류(특성) | 기본(업무서 바로 도출)·설계(설계 과정 부여)·파생(계산으로 도출)      |
| 파생 속성       | 총액·나이처럼 계산. 정합성 부담이 커 **가급적 최소화**가 정답 포인트 |
| 속성의 원자성   | 하나의 속성엔 하나의 값만. 다중값은 1정규형 위반 → 별도 엔터티       |
| 도메인          | 속성이 가질 수 있는 값의 범위(타입·길이·제약)                        |
| 구성 분류       | PK 속성·FK 속성·일반 속성                                            |

#### 자주 틀리는 함정

- **함정:** 파생 속성은 조회가 빨라지니 많을수록 좋다. **→ 바로잡기:** 원본이 바뀌면 함께 갱신해야 해 정합성 위험이 커진다. 최소화 가 원칙.
- **함정:** 하나의 속성에 값이 여러 개 들어갈 수 있다. **→ 바로잡기:** 속성은 원자값 하나 만. 여러 값이 필요하면 엔터티를 분리한다.

⏱ 30초 정리

분류 = **기본·설계·파생**(특성) / 단순·복합(분해) / 단일·다중값(개수). 파생 속성은 최소화. 속성 = 원자값 하나.

### 5. 관계 (Relationship)

> **정의** 관계란 두 엔터티가 서로 어떻게 연결되어 있는지 표현한 것이다.  
> ex) '회원 ─ 주문 : 주문하다/주문되다', '부서 ─ 사원 : 소속하다/소속되다'처럼 양방향 동사로 표현한다.

#### 관계의 4요소

| 요소           | 영문        | 설명                               | 예                                |
|----------------|-------------|------------------------------------|-----------------------------------|
| **관계명**     | Membership  | 두 엔터티를 잇는 동사·역할명       | 주문하다 / 주문되다               |
| **관계차수**   | Cardinality | 1:1, 1:N, M:N                      | 회원 1 : N 주문                   |
| **관계선택성** | Optionality | 필수(Mandatory) / 선택(Optional)   | 주문엔 반드시 회원이 있어야 하나? |
| **관계방향**   | Direction   | 양방향 표현(양쪽 관계명 모두 명명) | 회원→주문 / 주문→회원             |

#### 관계 차수(Cardinality) 3가지

| 차수      | 의미                                  | 예                                    |
|-----------|---------------------------------------|---------------------------------------|
| **1 : 1** | 서로 하나씩                           | 사원 ─ 사원증 (사원 1명당 사원증 1개) |
| **1 : N** | 한쪽이 하나일 때 상대는 여럿          | 부서 ─ 사원, 회원 ─ 주문              |
| **M : N** | 양쪽 모두 여럿 → **그대로 구현 불가** | 학생 ─ 과목                           |

> M:N 해소 M:N은 그대로 둘 수 없어 중간에 연결(교차) 엔터티 를 두어 1:N + N:1 로 분해합니다. (학생 ─ 수강 ─ 과목)

#### 관계 선택성(Optionality) & 식별 vs 비식별

| 구분             | 표기       | 의미                                                        |
|------------------|------------|-------------------------------------------------------------|
| 필수 (Mandatory) | `|` (막대) | 반드시 있어야 함 — \[회원\]──\[주문\]: 주문엔 반드시 회원   |
| 선택 (Optional)  | `○` (고리) | 있을 수도 없을 수도 — \[회원\]──○\[쿠폰\]: 쿠폰은 없을 수도 |

**식별 관계 (실선)**

자식의 PK에 부모 식별자가 포함 (강한 종속). 자식이 부모 없이 존재 불가. (주문 ↔ 주문상세)

**비식별 관계 (점선)**

부모 식별자가 자식의 일반 속성(FK) 으로만. 자식이 부모 없이도 존재 가능. (부서 ↔ 사원)

#### SQL 실전 — 관계는 외래키(FK)로 구현된다

    CREATE TABLE ORDERS (
        ORDER_ID   NUMBER PRIMARY KEY,
        MEMBER_ID  VARCHAR2(10),   -- 외래키(관계의 구현)
    CONSTRAINT FK_ORDER_MEMBER FOREIGN KEY(MEMBER_ID) REFERENCES MEMBER(MEMBER_ID)
    );
    -- 관계는 곧 조인이 된다 (설계의 1:N → ON 한 줄)
    SELECT M.NAME, O.ORDER_ID FROM MEMBER M JOIN ORDERS O ON M.MEMBER_ID = O.MEMBER_ID;

#### Before & After — M:N 관계의 분해

**BEFORE · M:N 그대로 → 다중값**

| 학생   | 듣는 과목들      |
|--------|------------------|
| 김철수 | 수학, 영어, 국어 |
| 이영희 | 영어, 과학       |

→

**AFTER · 교차 엔터티로 1:N + 1:N**

| 학생       |
|------------|
| S01 김철수 |
| S02 이영희 |

| 수강(교차) |
|------------|
| S01·K1     |
| S01·K2     |
| S02·K2     |

| 과목    |
|---------|
| K1 수학 |
| K2 영어 |

#### 시험 포인트

| 출제 포인트            | 시험에서 묻는 방식                                                     |
|------------------------|------------------------------------------------------------------------|
| 관계 차수              | 1:1, 1:M, M:N. ERD 까마귀발(다) 기호로 읽어내기                        |
| 관계 선택사양          | 필수 참여(\|) vs 선택 참여(○). "~없는 ~도 있을 수 있다" 진술의 참·거짓 |
| 관계의 페어링          | 인스턴스끼리 실제로 연결되는 각각의 짝. 관계는 페어링의 집합           |
| 존재 관계 vs 행위 관계 | ERD는 둘을 구분 안 함(하나의 표기). UML만 연관(실선)·의존(점선)        |
| M:N 해소               | 논리의 M:N → 물리에서 교차(연결) 엔터티로 분해                         |

#### 자주 틀리는 함정

- **함정:** ERD는 존재 관계와 행위 관계를 실선·점선으로 구분한다. **→ 바로잡기:** 구분하지 않는다. 실선·점선으로 구분하는 것은 UML 의 연관·의존.
- **함정:** IE와 Barker는 실선·점선의 의미가 같다. **→ 바로잡기:** IE는 식별·비식별 , Barker는 필수·선택 을 실선·점선으로 나타낸다.

⏱ 30초 정리

4요소 = 관계명·차수·선택성·방향. 차수 = 1:1·1:M·M:N. ○ = 선택 참여. M:N은 교차 엔터티로 해소. 식별=실선(PK 포함), 비식별=점선(FK만).

### 6. 식별자 (Identifier)

> **정의** 식별자란 엔터티 안의 인스턴스를 서로 구분해 주는 유일한 표식 이다. 테이블의 기본키(PK)가 된다.  
> ex) 같은 이름의 김철수가 100명 있어도 주민등록번호는 모두 다르다. 이름은 일반 속성, 주민번호는 식별자. PK는 자기 엔터티의 식별자, FK(외부식별자)는 다른 엔터티의 PK를 참조한 식별자.

#### 주식별자의 4가지 조건 — '유·최·불·존'

**1 · 유일성**

모든 인스턴스를 유일하게 구분.

**2 · 최소성**

꼭 필요한 속성만으로 구성 (정규화와 직결).

**3 · 불변성**

한 번 정해지면 거의 변하지 않음.

**4 · 존재성**

NULL이 될 수 없음 (NOT NULL).

> 참고 PRIMARY KEY 제약은 유일성 + NOT NULL 을 한꺼번에 강제 → 4조건 중 2가지가 DBMS 차원에서 자동 보장. ('대표성'은 아래 분류 기준의 개념으로, 교재에 따라 특성에 함께 넣기도 함)

#### 식별자의 4가지 분류 기준

| 기준        | 분류                        | 핵심 차이                                                   |
|-------------|-----------------------------|-------------------------------------------------------------|
| ① 대표성    | 주식별자 / 보조식별자       | 엔터티 대표 식별자(회원ID) vs 보조용(이메일·UNIQUE)         |
| ② 생성 여부 | 내부식별자 / 외부식별자     | 자기 엔터티에서 생성 vs 다른 엔터티 PK를 가져옴(= FK)       |
| ③ 속성 수   | 단일식별자 / **복합**식별자 | 1개 속성 vs 2개 이상 결합 (주문ID+상품ID)                   |
| ④ 대체 여부 | 본질식별자 / 인조식별자     | 업무 자연 도출(주민번호·학번) vs 인위적 부여(자동증가·UUID) |

#### SQL 실전 — PK / FK / 복합키

    -- 회원: 단일 PK + 보조식별자(UNIQUE)
    CREATE TABLE MEMBER (
        MEMBER_ID VARCHAR2(10) PRIMARY KEY,   -- 주식별자
        EMAIL     VARCHAR2(100) UNIQUE,       -- 보조식별자
        NAME      VARCHAR2(50) NOT NULL
    );
    -- 주문상세: 복합 PK (ORDER_ID + PROD_ID)
    CREATE TABLE ORDER_DETAIL (
        ORDER_ID NUMBER, PROD_ID VARCHAR2(10), QTY NUMBER,
        CONSTRAINT PK_OD PRIMARY KEY(ORDER_ID, PROD_ID)   -- 복합 식별자
    );
    INSERT INTO MEMBER VALUES('M01', 'a@a.com', '김철수');
    INSERT INTO MEMBER VALUES('M01', 'b@b.com', '박민수');  -- 에러! 유일성 위반(ORA-00001)
    INSERT INTO MEMBER VALUES(NULL, 'c@c.com', '이영희'); -- 에러! 존재성 위반(ORA-01400)

#### Before & After — 식별자를 잘못 잡으면

**BEFORE · 식별자 = 이름**

| NAME (PK?) | PHONE    |
|------------|----------|
| 김철수     | 010-1111 |
| 김철수     | 010-2222 |

동명이인 등록 불가 (유일성 위반)

→

**AFTER · 식별자 = 회원ID**

| ID (PK) | NAME   | PHONE    |
|---------|--------|----------|
| M01     | 김철수 | 010-1111 |
| M02     | 김철수 | 010-2222 |

동명이인이라도 ID로 구분

#### 시험 포인트

| 출제 포인트     | 시험에서 묻는 방식                                                                     |
|-----------------|----------------------------------------------------------------------------------------|
| 분류 기준 4가지 | 대표성(주/보조)·생성 여부(내부/외부)·속성 수(단일/복합)·대체 여부(본질/인조) 짝 맞추기 |
| 주식별자 4특성  | 유일성·최소성·불변성·존재성. 설명을 주고 명칭 고르기                                   |
| 주식별자 선정   | 자주 이용·이름 부여 지양·복합이면 속성 수 최소화                                       |
| 식별자 관계     | 부모 PK가 자식 PK에 포함. 자식은 부모 없이 존재 불가, 생명주기 공유                    |
| 비식별자 관계   | 부모 PK가 자식의 일반 속성(FK)으로만 전이. 자식 독립 존재 가능                         |

#### 자주 틀리는 함정

- **함정:** 업무상 값이 바뀔 수 있는 속성도 주식별자로 쓸 수 있다. **→ 바로잡기:** 주식별자는 불변성 을 만족해야 한다. 값이 바뀌면 참조 무결성이 깨진다.
- **함정:** 복합 식별자는 속성을 많이 넣을수록 안전하다. **→ 바로잡기:** 최소성 위반. 유일성을 만족하는 최소 집합만 포함한다.
- **함정:** 타 엔터티로부터 받아오는 식별자를 보조식별자라 한다. **→ 바로잡기:** 타 엔터티에서 받아오는 것은 외부 식별자 . 보조식별자는 대표성 없는 식별자.

⏱ 30초 정리

기준 4개 = 대표성·생성·개수·대체. 4특성 = **유·최·불·존**. 식별 관계=부모 PK 포함, 비식별=FK로만. '다중값 식별자'는 함정(없는 말).

# 데이터 모델과 SQL

정규화·관계와 조인·트랜잭션·NULL·식별자가 실제 SQL로 어떻게 이어지는지 다룹니다. **정규화 단계** 구분과 **관계=FK=JOIN** 흐름은 거의 매번 출제됩니다.

------------------------------------------------------------------------

### 1. 정규화 (Normalization)

> **정의** 정규화란 데이터의 중복을 없애고 이상현상을 막기 위해 테이블을 단계적으로 쪼개는 작업이다.  
> ex) 옷장 한 칸에 속옷·양말·셔츠를 다 욱여넣으면 찾기 어렵고 하나 빼다 다른 게 떨어진다. 칸을 종류별로 나누는 것이 정규화.

정규화하면 입력·수정·삭제 성능은 **일반적으로 향상**, 조회 성능은 조건에 따라 **향상되거나 저하**(조인 증가). 중복 제거 → 무결성↑, 저장공간↓.

#### 이상현상 (Anomaly) 3가지 — 정규화가 막으려는 것

**삽입 이상**

데이터를 넣으려는데 다른 정보가 없어 못 넣음. (학생 등록하려는데 수강과목 칸을 비울 수 없음)

**갱신 이상**

한 곳만 바꿨는데 다른 곳이 안 바뀜. (회원 주소 1곳만 수정 → 데이터 불일치)

**삭제 이상**

데이터를 지우려다 필요한 정보까지 사라짐. (마지막 수강 취소했는데 학생 정보까지 삭제)

#### 정규화 단계 한눈에 — 뒤로 갈수록 엄격해진다

    정규화 단계 (오른쪽으로 갈수록 더 엄격 / 순서: 1 → 2 → 3 → BCNF → 4 → 5)

     [비정규형]  --원자값/다중값 제거-->  [1NF]  --부분종속 제거-->  [2NF]  --이행종속 제거-->  [3NF]  --결정자=후보키-->  [BCNF]
     한칸 여러값                          한칸 한값               PK 전체에 종속           일반속성 간 종속 X          모든 결정자=후보키

| 단계                | 무엇을 없애나 (핵심 규칙)                                     | 키워드            |
|---------------------|---------------------------------------------------------------|-------------------|
| **제1정규화 (1NF)** | 모든 속성은 **하나의 값(원자값)**만 — 다중값·반복그룹 제거    | 원자값 / 반복그룹 |
| **제2정규화 (2NF)** | 일반 속성은 **주식별자 전체**에 종속 — **부분함수 종속** 제거 | 부분종속 제거     |
| **제3정규화 (3NF)** | 일반 속성끼리 종속 금지 — **이행함수 종속** 제거              | 이행종속 제거     |
| **BCNF**            | 모든 **결정자가 후보키**여야 함 (더 엄격한 3NF)               | 결정자 = 후보키   |

> 한 줄 암기 1NF=여러 값/반복 , 2NF=부분 종속 (복합키 일부에만 딸림), 3NF=이행 종속 (A→B→C라 A→C). 문제에 "부분" 보이면 2, "이행" 보이면 3!

#### 단계별로 직접 쪼개 보기 (학생 수강 예시)

**① 1NF — 한 칸에는 값 하나만 (원자값)** 한 셀에 "수학, 영어, 국어"처럼 여러 값이 있으면 1NF 위반. 행으로 풀어 한 칸에 한 값만.

**BEFORE · 비정규형**

| 학생   | 수강과목         |
|--------|------------------|
| 김철수 | 수학, 영어, 국어 |

→

**AFTER · 1NF**

| 학생   | 수강과목 |
|--------|----------|
| 김철수 | 수학     |
| 김철수 | 영어     |
| 김철수 | 국어     |

**② 2NF — 복합키 '일부'에만 딸린 속성 떼어내기 (부분종속 제거)** PK가 `(학생ID, 과목ID)`인데 '학생이름'은 학생ID에만, '과목명'은 과목ID에만 딸림(부분종속). 각자 테이블로 분리.

**BEFORE · 1NF (부분종속)**

| 학생ID (PK) | 과목ID (PK) | 학생이름 | 과목명 | 성적 |
|-------------|-------------|----------|--------|------|
| S01         | K1          | 김철수   | 수학   | 90   |
| S01         | K2          | 김철수   | 영어   | 85   |

→

**AFTER · 2NF (3개로 분리)**

| 학생ID | 학생이름 |
|--------|----------|
| S01    | 김철수   |

| 과목ID | 과목명 |
|--------|--------|
| K1     | 수학   |
| K2     | 영어   |

| 학생ID | 과목ID | 성적 |
|--------|--------|------|
| S01    | K1     | 90   |
| S01    | K2     | 85   |

> \*\*🔎 포인트\*\* 2NF는 PK가 2개 이상(복합키)일 때만 생기는 문제예요. PK가 단일 컬럼이면 부분종속이 있을 수 없어 1NF면 자동 2NF.

**③ 3NF — 키가 아닌 속성끼리의 종속 끊기 (이행종속 제거)** PK(사원ID) → 부서ID → 부서명 처럼 키가 아닌 '부서ID'를 거쳐 '부서명'이 정해지면 이행종속. '부서'를 별도 테이블로.

**BEFORE · 2NF (이행종속)**

| 사원ID (PK) | 부서ID | 부서명 |
|-------------|--------|--------|
| E01         | D1     | 영업부 |
| E02         | D1     | 영업부 |

→

**AFTER · 3NF**

| 사원ID | 부서ID |
|--------|--------|
| E01    | D1     |
| E02    | D1     |

| 부서ID | 부서명 |
|--------|--------|
| D1     | 영업부 |

**④ BCNF — 3NF인데도 남은 '이상한 결정자' 정리 (모든 결정자 = 후보키)** PK가 `(학생, 과목)`이고 "한 강사는 한 과목만 가르친다 → 강사가 과목을 결정"하면, 후보키 아닌 '강사'가 '과목'을 결정 → BCNF 위반. '강사' 기준으로 분리.

**BEFORE · 3NF이지만 BCNF 위반**

| 학생 (PK) | 과목 (PK) | 강사   |
|-----------|-----------|--------|
| S01       | 수학      | 김교수 |
| S02       | 수학      | 김교수 |
| S03       | 영어      | 이교수 |

→

**AFTER · BCNF**

| 강사   | 과목 |
|--------|------|
| 김교수 | 수학 |
| 이교수 | 영어 |

| 학생 | 강사   |
|------|--------|
| S01  | 김교수 |
| S02  | 김교수 |
| S03  | 이교수 |

> \*\*💡 한눈 정리\*\* 결정자(왼쪽에서 다른 속성을 결정하는 것)가 후보키이기만 하면 BCNF 만족. 시험은 보통 3NF까지 + "BCNF = 모든 결정자가 후보키"만 묻습니다.

#### SQL 실전 — 분리 후 JOIN으로 다시 합친다

    -- 정규화로 4개 테이블로 분리된 데이터를 다시 합쳐 조회
    SELECT O.ORDER_ID, C.CUST_NAME, P.PROD_NAME, D.QTY
      FROM ORDERS O
      JOIN CUSTOMER     C ON O.CUST_ID  = C.CUST_ID
      JOIN ORDER_DETAIL D ON O.ORDER_ID = D.ORDER_ID
      JOIN PRODUCT      P ON D.PROD_ID  = P.PROD_ID;
    -- 저장은 분산, 조회는 통합 — 정규화의 본질

#### 정규화의 장단점

| 장점                              | 단점                     |
|-----------------------------------|--------------------------|
| 데이터 중복 제거                  | 테이블이 많아짐          |
| 이상현상 방지 · 무결성↑           | 조인이 늘어남            |
| 입력·수정·삭제 성능·유지보수 용이 | 조회 성능 일부 저하 가능 |

#### 자주 틀리는 함정

- **함정:** 3정규화는 주식별자와 일반 속성 사이의 종속을 없애는 것이다. **→ 바로잡기:** 3NF는 일반 속성끼리의 이행 종속 제거. 주식별자와의 부분 종속은 2NF.
- **함정:** 정규화를 하면 성능이 무조건 나빠진다. **→ 바로잡기:** 조회는 불리할 수 있으나 입력·수정·삭제와 정합성은 좋아진다 .

⏱ 30초 정리

**1NF** 원자값(한 칸 한 값) → **2NF** 부분종속 제거(복합키 일부 딸림) → **3NF** 이행종속 제거(일반속성 간) → **BCNF** 모든 결정자=후보키. 정규화=저장 분산·조회 조인, 반정규화는 그 반대.

**❓ 확인 퀴즈 · 정규화**

정규화에 대한 설명이 아닌 것은?

1.  데이터 중복성을 제거한다.
2.  정규화할수록 엔터티는 증가한다.
3.  입력·수정·삭제 성능이 향상된다.
4.  조회 성능이 반드시 향상된다.

> 정답 ④ 정규화로 조인이 늘어 조회 성능이 저하될 수도 있습니다.

### 2. 반정규화 (De-Normalization) (보충)

조회 성능을 위해 **중복을 허용하거나 그룹핑**하는 과정. **정규화가 끝난 뒤** 성능 이슈가 있을 때만 고려합니다.

조회 성능 ↑, 그러나 입력·수정·삭제 성능 ↓ + **정합성(무결성) 저해** 위험. 신중해야 합니다.

| 구분                | 기법                                                         |
|---------------------|--------------------------------------------------------------|
| **테이블 반정규화** | 병합(1:1, 1:M) / 분할(수직·수평) / 추가(중복·통계·이력·부분) |
| **컬럼 반정규화**   | 중복 컬럼 추가 / 파생 컬럼 추가 / 이력 테이블 컬럼 추가      |
| **관계 반정규화**   | 중복 관계 추가                                               |

수직 분할

일부 **속성(컬럼)**을 별도 테이블로 → **1:1** 관계 2개. (자주 쓰는 컬럼 / NULL 많은 컬럼 분리)

수평 분할

일부 **인스턴스(행)**를 기준(주로 기간)으로 분할 = **파티셔닝**.

#### 슈퍼타입 / 서브타입 변환

| 타입       | 방식                       | 특징                                          |
|------------|----------------------------|-----------------------------------------------|
| One To One | 슈퍼·서브 각각 개별 테이블 | 테이블 많고 조인 多, 관리 어려움              |
| Plus       | 슈퍼+서브 테이블           | 조인 발생                                     |
| **Single** | 전부 하나의 테이블로 통합  | **조인 성능 best**, 관리 편리 (입출력은 나쁨) |

> 시험 포인트 수직=컬럼 분할(1:1), 수평=행 분할(파티셔닝). '백업 테이블 추가'는 반정규화 기법이 아님 (함정 — 추가 기법은 중복·통계·이력·부분).

**❓ 확인 퀴즈 · 반정규화**

반정규화의 기법이 아닌 것은?

1.  통계 테이블 추가
2.  백업 테이블 추가
3.  이력 테이블 추가
4.  부분 테이블 추가

> 정답 ② 테이블 추가 기법 = 중복·통계·이력·부분. '백업'은 포함되지 않습니다.

### 3. 관계와 조인의 이해 (관계=FK=JOIN)

> **정의** 모델에서의 관계는 외래키(FK) 로 구현되고, 그 관계를 따라 여러 테이블을 합쳐 보는 작업이 조인(JOIN) 이다.  
> ex) 영수증엔 주문만, 회원카드엔 회원만 있다. 같은 사람 것을 맞춰 보면 "김철수가 사과 2개 샀구나"가 보인다 — 키로 맞춰 합치는 것이 조인.

**1. 관계 (설계·개념 모델)** — 두 엔터티의 의미적 연결("회원이 주문을 한다")을 ERD 선으로 표현.

**2. 외래키 FK (논리·물리 모델)** — 자식 테이블이 부모 테이블의 PK를 참조하는 컬럼. FK = 조인 키 .

**3. 조인 JOIN (SQL 실행)** — FK = PK 조건으로 두 테이블을 합쳐 한 결과로 조회.

#### 조인의 4가지 종류 (개념 미리보기)

| 종류            | 의미                                   | 비유                     |
|-----------------|----------------------------------------|--------------------------|
| **INNER JOIN**  | 양쪽에 다 있는 것만 (교집합)           | 양쪽 카드 모두 가진 사람 |
| **LEFT OUTER**  | 왼쪽 다, 오른쪽은 매칭만 (없으면 NULL) | 왼쪽 기준                |
| **RIGHT OUTER** | 오른쪽 다, 왼쪽은 매칭만               | 오른쪽 기준              |
| **FULL OUTER**  | 양쪽 모두 다 (한쪽만 있어도 표시)      | 합집합                   |

*※ 상세 구문은 2과목 2-4 '꼭 나오는 SQL 보충'의 JOIN 파트에서 다룹니다.*

#### 관계 차수와 조인 결과 행 수

| 관계      | 조인 결과                                                               |
|-----------|-------------------------------------------------------------------------|
| **1 : 1** | 단순 매칭 — 행 수 그대로 (사원 ↔ 사원증)                                |
| **1 : N** | **행이 늘어남** — 회원 1명에 주문 3건이면 3행 (부모가 자식 수만큼 복제) |
| **M : N** | 교차 엔터티를 거쳐 **두 번 조인** (학생 → 수강 → 과목)                  |

#### SQL 실전 & Before & After — 1:N 조인은 N쪽 수만큼

**INPUT · 회원 2명 / 주문 3건**

| MEMBER     |
|------------|
| M01 김철수 |
| M02 이영희 |

| ORDERS  |
|---------|
| 1 · M01 |
| 2 · M01 |
| 3 · M02 |

→

**INNER JOIN 결과 · 3행**

| NAME   | ORDER_ID |
|--------|----------|
| 김철수 | 1        |
| 김철수 | 2        |
| 이영희 | 3        |

M01이 2번 복제 → 결과는 주문 건수(3)에 맞춰짐

#### 조인 시 자주 하는 실수

| 실수                           | 결과                     | 해결                        |
|--------------------------------|--------------------------|-----------------------------|
| 조인 조건(ON) 빠짐             | 카티션 곱(행 수 폭발)    | ON 명시                     |
| 1:N 관계인데 합계 계산         | 중복 합산(부풀림)        | DISTINCT 또는 서브쿼리 분리 |
| OUTER JOIN과 WHERE 혼동        | NULL 행이 빠짐           | OUTER JOIN 조건은 ON에 둠   |
| 교차 엔터티 생략하고 직접 조인 | 조인 키가 없어 카티션 곱 | 교차 엔터티 경유            |

#### 시험 포인트

| 출제 포인트          | 시험에서 묻는 방식                                                       |
|----------------------|--------------------------------------------------------------------------|
| 조인의 원리          | 두 엔터티의 PK-FK 값이 일치하는 인스턴스끼리 연결. 관계선이 곧 조인 경로 |
| 계층 관계            | 같은 엔터티 안의 부모-자식(자기 참조). 셀프 조인·계층형 질의로 조회      |
| 상호배타적(Arc) 관계 | 한 엔터티가 여러 엔터티 중 반드시 하나와만 연결. 반원으로 표기           |
| 교차 엔터티 경유     | M:N 해소한 교차 엔터티를 건너뛰면 조인 조건이 없어 카티션 곱             |

#### 자주 틀리는 함정

- **함정:** 중간 엔터티를 건너뛰고 양쪽을 바로 조인해도 된다. **→ 바로잡기:** 연결할 키가 없어 카티션 곱이 된다. 교차 엔터티를 경유 해야 한다.
- **함정:** 비식별자 관계로 바꾸면 조인이 줄어 조회가 빨라진다. **→ 바로잡기:** 키가 전파되지 않아 상위 엔터티까지 가려면 조인이 더 필요해진다.

⏱ 30초 정리

관계=FK=JOIN. 조인=PK·FK 값 일치. 1:N 조인 결과 행 수는 N쪽 수만큼. 교차 엔터티 생략=카티션 곱. Arc(상호배타)=여럿 중 하나와만.

### 4. 모델이 표현하는 트랜잭션의 이해

> **정의** 트랜잭션이란 함께 성공하거나 함께 실패해야 하는 데이터 작업의 묶음이다. 모델은 이 묶음을 관계의 필수성과 식별성 으로 표현한다.  
> ex) 계좌 이체는 A에서 1만원 출금 + B에 1만원 입금이 한 묶음. A에서만 빠지고 멈추면 돈이 사라지므로, 둘 다 성공하거나 둘 다 취소되어야 한다.

#### 트랜잭션 4대 특징 — ACID (원·일·고·지)

**원자성 (Atomicity)**

모두 성공하거나 모두 실패 — 이체는 출금+입금 한 묶음.

**일관성 (Consistency)**

트랜잭션 전후 무결성 규칙 유지 — 잔고 합계는 변하지 않음.

**고립성 (Isolation)**

동시 실행이라도 서로 간섭 없음 — 다른 사람 이체와 겹치지 않음.

**지속성 (Durability)**

커밋되면 시스템이 죽어도 보존 — 영수증으로 기록됨.

#### 트랜잭션 상태 흐름

| 상태                | 설명                               |
|---------------------|------------------------------------|
| Active (활성)       | BEGIN / 첫 DML ~ 실행 중           |
| Partially Committed | 마지막 SQL까지 무사 통과           |
| **Committed**       | COMMIT으로 영구 반영               |
| Failed → Aborted    | 오류 발생 → ROLLBACK으로 취소 종료 |

#### 모델에서 트랜잭션은 어떻게 보이나 — 관계의 필수성·식별성

| 모델 단서                     | 의미 · 트랜잭션 처리                                                                |
|-------------------------------|-------------------------------------------------------------------------------------|
| **관계의 필수성** (필수)      | 주문 INSERT 시 주문상세도 함께 INSERT → 한 트랜잭션                                 |
| **관계의 식별성** (식별·실선) | 주문상세는 주문 PK를 자기 PK로 가짐 → 주문 없이 존재 불가. DELETE 시 함께 처리/차단 |
| 선택 관계 (Optional)          | 고객은 주문이 없을 수 있음 → 각각 별도 트랜잭션으로 처리 가능                       |

#### SQL 실전 — 한 묶음으로 COMMIT / ROLLBACK

    -- 주문 1건 + 주문상세 2건을 한 트랜잭션으로
    INSERT INTO ORDERS VALUES(1001, 'C001', SYSDATE);
    INSERT INTO ORDER_DETAIL VALUES(1001, 'P01', 2);
    INSERT INTO ORDER_DETAIL VALUES(1001, 'P02', 1);
    COMMIT;      -- 한 묶음으로 영구 저장
    -- 중간 오류 시 ROLLBACK 하면 3개 INSERT가 통째로 사라짐(원자성)
    -- SAVEPOINT: 일부만 되돌리기
    INSERT A; SAVEPOINT S1; UPDATE B; ROLLBACK TO S1; INSERT D; COMMIT;
    -- 최종 반영 = INSERT A + INSERT D (UPDATE B만 취소)

#### Before & After — 트랜잭션이 깨지면

**BEFORE · 묶지 않음(출금만 성공)**

| 계좌 | 잔고              |
|------|-------------------|
| A    | 90,000 (1만 빠짐) |
| B    | 50,000 (그대로)   |

1만원이 증발 (원자성 깨짐)

→

**AFTER · 한 트랜잭션 + ROLLBACK**

| 계좌 | 잔고               |
|------|--------------------|
| A    | 100,000 (원상복구) |
| B    | 50,000             |

데이터가 보존됨

#### 시험 포인트

| 출제 포인트            | 시험에서 묻는 방식                                                   |
|------------------------|----------------------------------------------------------------------|
| ACID                   | 원자성(All-or-Nothing)·일관성·고립성(간섭 차단)·지속성(커밋 후 영구) |
| 필수 관계와 트랜잭션   | 양쪽 모두 필수 참여면 두 엔터티가 하나의 트랜잭션으로 묶임           |
| 선택 관계와 트랜잭션   | 한쪽이 선택 참여면 각각 별도 트랜잭션으로 처리 가능                  |
| 식별자 관계와 생명주기 | 부모가 사라지면 자식도 사라져야 하는 구조. 생명주기 공유             |
| 상황 판별형            | 미커밋 데이터 읽음 → 고립성 위반, 커밋 후 유실 → 지속성 위반         |

#### 자주 틀리는 함정

- **함정:** 원자성과 일관성은 같은 말이다. **→ 바로잡기:** 원자성=전부 반영 또는 전부 취소, 일관성=전후로 무결성 규칙이 지켜짐.
- **함정:** 관계가 선택 참여여도 반드시 한 트랜잭션으로 묶어야 한다. **→ 바로잡기:** 선택 참여면 따로 발생할 수 있으므로 별도 트랜잭션 으로 처리 가능.

⏱ 30초 정리

ACID = 원자·일관·고립·지속. 양쪽 필수(식별) 관계 = 한 트랜잭션. 미커밋 값 읽기 = 고립성 위반, 커밋 후 유실 = 지속성 위반. SAVEPOINT = 일부만 롤백.

### 5. Null 속성의 이해

> **정의** NULL이란 값이 없거나 아직 모름을 나타내는 특수한 표시다. 0이나 공백과는 전혀 다르다.  
> ex) "월 소득: 0원"은 0이라는 값, "월 소득: ␣"은 공백 문자, "월 소득: 미작성"이 NULL(값 자체가 없음).

#### NULL vs 0 vs 공백

| 비교        | 숫자 0 | 공백 ' '          | NULL                    |
|-------------|--------|-------------------|-------------------------|
| 데이터 존재 | 있음   | 있음 (문자 한 칸) | **없음**                |
| 비교 가능   | 가능   | 가능              | **불가** (= NULL 안 됨) |
| 산술 연산   | 가능   | —                 | **불가** (결과 NULL)    |

#### NULL 4가지 규칙 & 3-값 논리

| 규칙                  | 내용                                                  |
|-----------------------|-------------------------------------------------------|
| 산술 연산             | 결과는 NULL (1000 + NULL = NULL)                      |
| 비교 연산             | 결과는 UNKNOWN(3-값 논리) → WHERE에서 행 제외         |
| IS NULL / IS NOT NULL | `= NULL`, `!= NULL`은 항상 거짓 → 반드시 IS NULL 사용 |
| 집계 함수             | NULL을 무시. **COUNT(\*)만 NULL 포함**                |

> \*\*🔎 SQL 3-값 논리\*\* 일반 프로그래밍은 TRUE/FALSE 2값이지만, SQL은 NULL 때문에 TRUE / FALSE / UNKNOWN 3값입니다. NULL = NULL 도 UNKNOWN. WHERE는 TRUE인 행만 남기므로 = NULL 은 항상 0건.

#### NULL 처리 함수

| 함수                  | 동작                                |
|-----------------------|-------------------------------------|
| `NVL(A, B)`           | A가 NULL이면 B, 아니면 A            |
| `NVL2(A, B, C)`       | A가 NULL이 **아니면** B, NULL이면 C |
| `NULLIF(A, B)`        | A = B이면 NULL, 다르면 A            |
| `COALESCE(A, B, C …)` | NULL이 **아닌 최초**의 값 반환      |

#### 집계 함수에서의 NULL

| EMP (SAL)          | 쿼리       | 결과                      |
|--------------------|------------|---------------------------|
| A=100 B=NULL C=200 | COUNT(\*)  | 3 (NULL 행 포함)          |
|                    | COUNT(SAL) | 2 (NULL 제외)             |
|                    | SUM(SAL)   | 300                       |
|                    | AVG(SAL)   | 150 (300/2 — 0 포함 아님) |

#### SQL 실전 & Before & After — NULL이 끼면 결과가 달라진다

    SELECT * FROM EMP WHERE COMM = NULL;      -- 결과 0건 (잘못)
    SELECT * FROM EMP WHERE COMM IS NULL;     -- 올바름
    SELECT NAME, NVL(COMM, 0) FROM EMP;             -- NULL → 0 대체
    SELECT COALESCE(PHONE, EMAIL, '연락처 없음') FROM MEMBER;  -- 첫 비-NULL

**BEFORE · SAL + COMM (그대로)**

| NAME | SAL+COMM |
|------|----------|
| A    | 110      |
| B    | NULL     |
| C    | 320      |

COMM이 NULL인 B의 총급여가 사라짐

→

**AFTER · SAL + NVL(COMM,0)**

| NAME | TOTAL |
|------|-------|
| A    | 110   |
| B    | 200   |
| C    | 320   |

NULL을 0으로 치환 → 누락 없음

#### NULL과 정렬

| DBMS   | 기본 정렬 시 NULL 위치                                |
|--------|-------------------------------------------------------|
| Oracle | 오름차순(ASC)에서 **마지막**, 내림차순(DESC)에서 처음 |
| MS-SQL | 오름차순에서 **처음**                                 |

*※ 직접 지정: ORDER BY COL NULLS FIRST / NULLS LAST*

#### 시험 포인트 & 자주 틀리는 함정

- **함정:** AVG는 NULL을 0으로 보고 전체 건수로 나눈다. **→ 바로잡기:** NULL 행은 분자·분모 모두에서 제외. 0으로 보려면 AVG(NVL(컬럼,0)) .
- **함정:** NOT IN 서브쿼리에 NULL이 있어도 결과는 같다. **→ 바로잡기:** 비교가 UNKNOWN이 되어 한 건도 안 나올 수 있다. NOT EXISTS 는 영향 없음.

⏱ 30초 정리

NULL과의 산술=NULL. 집계는 NULL 제외, **COUNT(\*)만 포함**. 비교는 IS NULL/IS NOT NULL. 대체=NVL·NVL2·NULLIF·COALESCE. Oracle ASC는 NULL이 마지막.

### 6. 본질식별자 vs 인조식별자

> **정의** 본질식별자는 업무에서 자연스럽게 도출된 식별자, 인조식별자는 인위적으로 만든 식별자다. 둘의 장단점을 알고 상황에 맞게 선택한다.  
> ex) 도서관에서 ISBN(출판사 부여=본질식별자)과 자체 분류번호 A-001(임의 부여=인조식별자)로 책을 구분. ISBN이 길고 형식이 들쑥날쑥해 자체 번호를 더 자주 쓴다.

**본질식별자 (Natural)**

업무에서 자연 도출 · 의미 있음 · 변경 위험 존재. (주민번호·사업자번호·ISBN)

**인조식별자 (Surrogate)**

인위적으로 부여 · 의미 없음 · 변경에 자유. (자동증가 ID·UUID·GUID)

#### 비교표

| 항목             | 본질식별자               | 인조식별자                         |
|------------------|--------------------------|------------------------------------|
| 출처             | 업무에서 자연 발생       | 인위적으로 부여                    |
| 의미             | 업무적 의미 있음         | 의미 없음 (단순 키)                |
| 변경 위험        | 있음 (업무 규칙 변동 시) | 없음 (부여 후 영구 고정)           |
| 길이             | 길 수 있음               | 짧고 일관                          |
| 데이터 품질 검증 | 가능 (중복 자연 검출)    | 어려움 (본질키에 별도 UNIQUE 필요) |
| PK 사용 시 장점  | 의미 검증 용이 · 직관적  | JOIN/인덱스/관리 효율 · 보안       |

#### 언제 무엇을 쓸까 — 권장 패턴

> **현업 권장** PK는 인조식별자 (짧은 ID)로 두고, 본질키는 UNIQUE 제약 으로 별도 보존 → 보안·성능·일관성을 모두 만족.  
> 본질키를 PK로 쓰면 정규화 단계의 종속성 분석이 자연스럽지만, 변경 위험이 따른다는 점을 고려.

#### SQL 실전 — 인조 PK + 본질키 UNIQUE

    -- 인조식별자 PK + 본질키(ISBN)는 UNIQUE로 무결성 보존
    CREATE TABLE BOOK (
        BOOK_ID  NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- 인조식별자
        ISBN     VARCHAR2(20) UNIQUE,     -- 본질키는 UNIQUE로 유지
        TITLE    VARCHAR2(200)
    );
    INSERT INTO BOOK(ISBN, TITLE) VALUES('978-89-1234', 'SQL');
    INSERT INTO BOOK(ISBN, TITLE) VALUES('978-89-1234', 'SQL');  -- 에러! UNIQUE 위반 → 중복 입력 차단

#### Before & After — 인조식별자 도입의 효과

**BEFORE · 본질식별자(주민번호)를 PK로**

| ORDER (FK)             |
|------------------------|
| 800101-1234567 → 주문1 |
| 800101-1234567 → 주문2 |

자식 테이블마다 주민번호가 흩뿌려짐 → 개인정보 노출 위험

→

**AFTER · 인조식별자(M01) 도입**

| MEMBER                 |
|------------------------|
| M01 · RRN(UQ) · 김철수 |

| ORDER (FK) |
|------------|
| 1 · M01    |
| 2 · M01    |

자식엔 의미 없는 짧은 ID만 → 보안·JOIN 효율↑

#### 시험 포인트

| 출제 포인트      | 시험에서 묻는 방식                                                  |
|------------------|---------------------------------------------------------------------|
| 본질 식별자      | 업무에서 자연 발생한 식별자(주문번호·사업자번호 등)                 |
| 인조 식별자      | 업무엔 없지만 관리 편의로 임의 부여한 일련번호형 식별자             |
| 인조를 쓰는 경우 | 본질키가 복합키로 너무 길거나, 자주 바뀌거나, 의미 노출이 곤란할 때 |
| 인조의 부작용    | 본질적으로 같은 데이터가 서로 다른 일련번호로 중복 입력될 수 있음   |
| 판별형           | "업무 행위 없이도 부여될 수 있다" → 인조 식별자의 특성              |

#### 자주 틀리는 함정

- **함정:** 인조 식별자를 쓰면 항상 설계가 좋아진다. **→ 바로잡기:** 유일성 검증 장치가 없으면 중복 저장될 수 있다. 본질키에 UNIQUE 를 함께 건다.
- **함정:** 본질 식별자는 업무 행위 없이도 부여할 수 있다. **→ 바로잡기:** 본질 식별자는 업무 수행 과정에서 값이 정해진다. 업무와 무관하게 부여되면 인조 식별자.

⏱ 30초 정리

본질=업무에서 발생(주민번호·ISBN). 인조=임의 부여·복합키 대체(자동증가·UUID). 권장=인조 PK + 본질키 UNIQUE. 인조는 중복 입력 위험을 동반.

# SQL 기본

2과목은 40문항(전체 80%)으로 합격의 핵심입니다. 먼저 관계형 DB 개념과 SELECT, 그리고 단골 출제 **함수**들을 익힙니다.

------------------------------------------------------------------------

### 1. 관계형 데이터베이스 기본 용어

> \*\*💡 쉽게 말하면\*\* 관계형 DB는 모든 데이터를 엑셀 같은 2차원 표 로 저장합니다. 가로줄 = 행(Row), 세로칸 = 열(Column). SQL은 이 표에 "조회/수정/삭제해줘"라고 말하는 DB 전용 언어 예요.

| 데이터 모델 용어 | DB 테이블 용어         |
|------------------|------------------------|
| 엔터티(Entity)   | **테이블**(Table)      |
| 인스턴스(행)     | **로우**(Row / 레코드) |
| 속성(Attribute)  | **컬럼**(Column)       |

> RDBMS 예 Oracle, SQL Server(MSSQL), MySQL, MariaDB, PostgreSQL — 관계형 DB를 관리하는 시스템들입니다.

### 2. SELECT 문 & 연산자

    SELECT 컬럼1, 컬럼2  -- 조회할 컬럼 (*는 전체)
    FROM 테이블 T  -- 별칭(Alias) T 부여
    WHERE 컬럼1 = '아무개';  -- 조건(없으면 전체 행)

> 시험 포인트 테이블에 별칭(Alias) 을 붙이면, 그 뒤부터는 반드시 별칭을 써야 합니다. FROM TAB T 했으면 TAB.COL 이 아니라 T.COL . Alias 앞 AS 는 생략 가능.

| 연산자         | 설명                                       |
|----------------|--------------------------------------------|
| 산술 (+ − × ÷) | 숫자·날짜 계산. **NULL 포함 시 결과 NULL** |
| 합성 (`||`)    | 문자 + 문자 연결 (CONCAT과 같음)           |

### 3. 문자 함수

| 함수                       | 기능                                 | 예 → 결과                            |
|----------------------------|--------------------------------------|--------------------------------------|
| `LOWER / UPPER`            | 소문자 / 대문자 변환                 | UPPER('iu') → IU                     |
| `LTRIM / RTRIM`            | 왼쪽/오른쪽 공백(또는 지정문자) 제거 | LTRIM('블랙핑크','블랙') → 핑크      |
| `TRIM`                     | 양쪽 제거 (지정문자는 **한 글자**만) | TRIM(' IU ') → IU                    |
| `SUBSTR(문자,시작[,길이])` | 문자열 일부 자르기                   | SUBSTR('블랙핑크제니',3,2) → 핑크    |
| `LENGTH`                   | 문자열 길이                          | LENGTH('블랙핑크') → 4               |
| `REPLACE(문자,전[,후])`    | 치환 (후 생략 시 제거)               | REPLACE('제니','제니','지수') → 지수 |
| `LPAD(문자,길이,채울문자)` | 왼쪽을 채워 지정 길이로              | LPAD('IU',4,'V') → VVIU              |

> 핵심 LTRIM/RTRIM 은 지정 문자를 여러 글자 비교(한 글자씩, 포함 안 되면 멈춤), TRIM 은 한 글자 만 지정 가능.

### 4. 숫자 함수

| 함수               | 기능                          | 예 → 결과               |
|--------------------|-------------------------------|-------------------------|
| `ABS`              | 절댓값                        | ABS(-1) → 1             |
| `SIGN`             | 부호 (양1·음−1·0)             | SIGN(-7) → -1           |
| `ROUND(수[,자리])` | 반올림                        | ROUND(163.76,1) → 163.8 |
| `TRUNC(수[,자리])` | 버림(절삭)                    | TRUNC(54.29,1) → 54.2   |
| `CEIL`             | 올림(크거나 같은 최소 정수)   | CEIL(72.1) → 73         |
| `FLOOR`            | 내림(작거나 같은 최대 정수)   | FLOOR(72.9) → 72        |
| `MOD(수1,수2)`     | 나머지 (수2가 0이면 수1 반환) | MOD(15,7) → 1           |

> 헷갈림 주의 음수에서 CEIL(-33.4)=-33 (올림이니 0에 가까움), FLOOR(-22.3)=-23 (내림이니 더 작게). MOD(n,0)=n 꼭 기억!

### 5. 날짜 · 변환 함수

| 함수                            | 기능                                             |
|---------------------------------|--------------------------------------------------|
| `SYSDATE`                       | 현재 날짜·시간                                   |
| `EXTRACT(YEAR FROM 날짜)`       | 연/월/일 등 특정 단위 추출                       |
| `ADD_MONTHS(날짜, n)`           | n개월 더함. 해당 일자 없으면 **그 달 말일** 반환 |
| `TO_NUMBER / TO_CHAR / TO_DATE` | 숫자↔문자↔날짜 **명시적** 형변환                 |

> \*\*🔎 명시적 vs 암시적 형변환\*\* 명시적: TO_CHAR 등 함수로 직접 변환. 암시적: DB가 알아서 변환. 암시적은 인덱스를 못 써 성능이 나빠질 수 있어 명시적 변환 권장 . (예: ADD_MONTHS(DATE '2022-01-31', 1) → 2월 말일 '2022-02-28')

### 6. NULL 관련 함수 (매우 중요)

| 함수                  | 동작                                |
|-----------------------|-------------------------------------|
| `NVL(A, B)`           | A가 NULL이면 B, 아니면 A            |
| `NVL2(A, B, C)`       | A가 NULL이 **아니면** B, NULL이면 C |
| `NULLIF(A, B)`        | A=B이면 NULL, 다르면 A              |
| `COALESCE(A, B, C …)` | NULL이 **아닌 최초**의 값 반환      |

> 암기팁 NVL = " N ull이면 V alue 대체". NVL2는 인수 3개(아니면·맞으면 순서 주의). COALESCE = 여러 개 중 첫 유효값.

# SQL 활용

서브쿼리·뷰·집합 연산자·그룹 함수를 다룹니다. 계층형 쿼리·윈도우 함수는 기출 파트에서 함께 정리합니다.

------------------------------------------------------------------------

### 1. 서브쿼리 (Subquery)

쿼리 안의 또 다른 쿼리. 바깥=**메인쿼리**, 안=**서브쿼리**입니다.

> \*\*💡 쉽게 말하면\*\* 아기를 품은 엄마를 떠올리세요. 엄마(메인쿼리) 안에 아기(서브쿼리)가 있죠. 서브쿼리가 먼저 답을 구해 메인쿼리에 건네줍니다.

#### 위치에 따른 분류

| 이름                | 위치              | 설명                                        |
|---------------------|-------------------|---------------------------------------------|
| **스칼라 서브쿼리** | SELECT 절         | 반드시 **값 1개**만 반환 (컬럼 자리에 사용) |
| **인라인 뷰**       | FROM 절           | 임시 테이블처럼 사용                        |
| **중첩 서브쿼리**   | WHERE / HAVING 절 | 조건 비교에 사용                            |

#### 반환 형태에 따른 분류

| 종류      | 특징           | 함께 쓰는 연산자                         |
|-----------|----------------|------------------------------------------|
| 단일 행   | 1건 이하 반환  | `=`, `>`, `<` …                          |
| 다중 행   | 2건 이상 반환  | `IN`, `ANY`, `ALL`, `EXISTS` (`=` 불가!) |
| 다중 컬럼 | 여러 컬럼 반환 | `IN` 등                                  |

> 시험 포인트 다중 행 서브쿼리에 = 를 쓰면 에러 . IN 을 써야 합니다. 연관 서브쿼리 = 메인쿼리 컬럼을 포함, 비연관 = 포함 안 함.

### 2. 뷰 (View)

SELECT 문에 이름을 붙여 재사용하는 **가상 테이블**. 실제 데이터는 저장하지 않습니다.

**독립성**

테이블 구조가 바뀌어도 뷰만 고치면 됨.

**편리성**

복잡한 쿼리를 뷰 이름으로 단순화.

**보안성**

민감 컬럼은 빼고 뷰 생성 → 정보 감춤.

> 함정 뷰의 특징은 독립성·편리성·보안성. '투명성'은 아님 (뷰 생성 SQL을 사용자가 볼 수 없으므로). 뷰는 인덱스 구성 불가, 삽입·수정·삭제에 제약이 많음.

### 3. 집합 연산자

| 연산자           | 의미            | 중복                      |
|------------------|-----------------|---------------------------|
| `UNION ALL`      | 합집합 (그대로) | 중복 **유지**             |
| `UNION`          | 합집합          | 중복 **제거**(+정렬 부하) |
| `INTERSECT`      | 교집합(공통)    | 중복 제거                 |
| `MINUS / EXCEPT` | 차집합(앞 − 뒤) | 중복 제거                 |

> 핵심 ① 결과의 헤더(컬럼명)는 첫 번째 쿼리 를 따라감. ② ORDER BY는 맨 마지막에 한 번만 . ③ MINUS=Oracle, EXCEPT=SQL Server(같은 차집합).

### 4. 그룹 함수 (ROLLUP · CUBE · GROUPING SETS)

소계(소그룹별 합)와 총계를 구하는 함수들입니다. 이게 SQL 활용에서 제일 어렵지만, **"무엇으로 그룹핑되는가"**만 비교하면 됩니다.

| 함수                 | 그룹핑 결과 (A, B 기준)                                                         |
|----------------------|---------------------------------------------------------------------------------|
| `ROLLUP(A,B)`        | ①A,B별 ②A별 ③**총계**  <span style="color:var(--muted)">(한 방향 소계)</span>   |
| `CUBE(A,B)`          | ①A,B별 ②A별 ③B별 ④**총계**  <span style="color:var(--muted)">(모든 조합)</span> |
| `GROUPING SETS(A,B)` | ①A별 ②B별  <span style="color:var(--muted)">(지정한 것만, 총계 없음)</span>     |

> \*\*💡 핵심 직관\*\* ROLLUP = 계단식 소계(왼→오 한 방향). CUBE = 가능한 모든 조합 의 소계(다차원). GROUPING SETS = 내가 지정한 묶음만 개별 집계. 총계가 필요하면 인자에 () 를 추가하거나 ROLLUP을 쓰면 됩니다.

> 시험 포인트 괄호 묶음은 "한 덩어리"로 취급. ROLLUP((A,B), C) → (A,B),C별 → (A,B)별 → 총계. "결합 가능한 모든 집계" = CUBE .

**❓ 확인 퀴즈 · 집합 연산자**

차집합과 같은 역할을 하는 집합 연산자는?

1.  UNION
2.  MINUS (= EXCEPT)
3.  INTERSECT
4.  UNION ALL

> 정답 ② 차집합 = MINUS(Oracle) / EXCEPT(SQL Server). 교집합은 INTERSECT.

# 관리 구문

SQL 명령어를 4종류로 나눠 익힙니다. **DML·TCL·DDL·DCL** — 어느 명령어가 어디 속하는지가 단골 출제 포인트입니다.

------------------------------------------------------------------------

| 분류    | 풀이            | 명령어                                   |
|---------|-----------------|------------------------------------------|
| **DML** | 데이터 조작어   | INSERT, UPDATE, DELETE, (SELECT), MERGE  |
| **TCL** | 트랜잭션 제어어 | COMMIT, ROLLBACK, SAVEPOINT              |
| **DDL** | 데이터 정의어   | CREATE, ALTER, DROP, RENAME, TRUNCATE    |
| **DCL** | 데이터 제어어   | GRANT, REVOKE (+ CREATE/ALTER/DROP USER) |

> 암기팁 헷갈리는 두 가지: COMMIT/ROLLBACK은 TCL (DDL 아님!), TRUNCATE는 DDL (DML 아님!). GRANT/REVOKE는 DCL.

### 1. DML — 데이터 조작어

| 명령어   | 설명                                                       | 주의                                               |
|----------|------------------------------------------------------------|----------------------------------------------------|
| `INSERT` | 데이터 입력                                                | PK·NOT NULL 컬럼엔 NULL 입력 불가                  |
| `UPDATE` | 데이터 수정                                                | **WHERE 없으면 전체 행** 수정                      |
| `DELETE` | 데이터 삭제                                                | WHERE 없으면 전체 행 삭제. COMMIT 전 ROLLBACK 가능 |
| `MERGE`  | 입력+수정을 한 번에 (ON 조건으로 MATCHED/NOT MATCHED 분기) | 동기화·백업에 유용                                 |

> \*\*🔎 DELETE vs TRUNCATE vs DROP\*\* DELETE : 행만 삭제, ROLLBACK 가능, 로그 남김. TRUNCATE : 전체 행 삭제 + 저장공간 초기화, ROLLBACK 불가 (DDL), 빠름, 구조는 유지. DROP : 테이블 구조까지 통째 삭제. "연인과 깔끔히 헤어지는 TRUNCATE, 미련 남기는 DELETE"로 기억!

> 시험 포인트 1억 건을 로그 없이 빠르게 비우고 테이블은 유지 → TRUNCATE . DML은 COMMIT해야 디스크 반영(단 SQL Server는 DML도 AUTO COMMIT).

### 2. TCL — 트랜잭션 제어어

| 명령어      | 설명                                                      |
|-------------|-----------------------------------------------------------|
| `COMMIT`    | 변경 내용 **확정·반영**. 해야 최종 저장                   |
| `ROLLBACK`  | 변경 내용 **취소**, 이전 값 복구                          |
| `SAVEPOINT` | 중간 지점 저장 → `ROLLBACK TO 지점`으로 **일부만** 되돌림 |

> 핵심 COMMIT 전까지는 메모리에만 있어 다른 사용자는 못 봄. 오래 COMMIT/ROLLBACK 안 하면 LOCK 이 걸려 남이 수정 못 함.

### 3. DDL — 데이터 정의어

#### 데이터 유형 — CHAR vs VARCHAR

**CHAR (고정 길이)**

정한 크기를 항상 다 차지 . 'IU'를 CHAR(10)에 넣으면 10byte. 비교 시 공백 무시 → 'IU'='IU  '.

**VARCHAR (가변 길이)**

실제 크기만 사용. 'IU'는 2byte. 비교 시 공백도 문자 → 'IU'≠'IU  '.

*※ 영어 1글자=1byte, 한글 1글자=3byte(캐릭터셋에 따라 2byte)로 크기를 계산.*

#### 주요 명령어

| 명령어                    | 설명                                                      |
|---------------------------|-----------------------------------------------------------|
| `CREATE TABLE`            | 테이블 생성 (컬럼·데이터유형·크기·제약조건 정의)          |
| `ALTER ... ADD`           | 컬럼/제약조건 추가 (컬럼은 항상 맨 끝에)                  |
| `ALTER ... MODIFY`        | 데이터유형·DEFAULT·NOT NULL 변경                          |
| `ALTER ... DROP COLUMN`   | 컬럼 삭제 (복구 불가)                                     |
| `ALTER ... RENAME COLUMN` | 컬럼명 변경                                               |
| `DROP TABLE`              | 테이블 삭제. 참조 테이블 있으면 `CASCADE CONSTRAINT` 필요 |
| `TRUNCATE TABLE`          | 전체 행 삭제 + 공간 초기화 (ROLLBACK 불가)                |

> \*\*🔎 CTAS & 제약조건\*\* CTAS ( CREATE TABLE ~ AS SELECT ~ ): 기존 테이블 복사 생성. 단 NOT NULL만 복사 되고 PK·UNIQUE·CHECK는 초기화 → 필요 시 ALTER로 재정의. 제약조건 : PRIMARY KEY, UNIQUE, NOT NULL, CHECK(값 범위 지정), FOREIGN KEY(참조 무결성).

> 시험 포인트 컬럼 데이터유형/DEFAULT/NOT NULL 변경 → MODIFY . 컬럼 추가 → ADD . CASCADE는 Oracle만 있고 SQL Server엔 없음.

### 4. DCL — 데이터 제어어

> \*\*💡 쉽게 말하면\*\* DB를 '집'이라 하면 USER는 '룸메이트'. 먼저 사람을 들이고(CREATE USER + 비밀번호), 집을 쓸 권한 을 줘야(GRANT) 방에 들어갈 수 있어요. 권한 회수는 REVOKE.

| 명령어                    | 설명                                                                     |
|---------------------------|--------------------------------------------------------------------------|
| `GRANT 권한 TO 사용자`    | 권한 부여 (예: GRANT CREATE TABLE TO PERPEAR)                            |
| `REVOKE 권한 FROM 사용자` | 권한 회수                                                                |
| `ROLE`                    | 여러 권한을 하나로 묶은 **세트** (빅맥세트처럼). ROLE을 사용자에게 GRANT |

**❓ 확인 퀴즈 · 명령어 분류**

다음 중 DDL이 아닌 것은?

1.  CREATE TABLE
2.  COMMIT
3.  ALTER
4.  RENAME

> 정답 ② COMMIT은 TCL. DDL은 CREATE·ALTER·DROP·RENAME·TRUNCATE입니다.

# 꼭 나오는 SQL 보충

교안에는 간략했지만 **기출에 반드시 나오는** 조인·계층형 쿼리·윈도우 함수·연산자 우선순위·CASE를 한 번에 정리했습니다. 2과목 고득점의 열쇠입니다.

------------------------------------------------------------------------

### 1. JOIN (조인)

두 테이블을 연결해 조회합니다. 결과 건수를 묻는 문제가 자주 나옵니다.

| 종류            | 설명                                      |
|-----------------|-------------------------------------------|
| **INNER JOIN**  | 양쪽에 **모두 있는** 행만 (교집합)        |
| **LEFT OUTER**  | 왼쪽 전부 + 매칭되는 오른쪽 (없으면 NULL) |
| **RIGHT OUTER** | 오른쪽 전부 + 매칭되는 왼쪽               |
| **FULL OUTER**  | 양쪽 전부 (매칭+비매칭 모두)              |
| **CROSS JOIN**  | 두 테이블 행의 **곱** (카테시안 곱)       |

> 시험 포인트 ① INNER JOIN에서 ON이 빠지면 CROSS JOIN 과 같은 결과(행의 곱). ② Oracle의 (+) 는 ANSI OUTER JOIN으로 변환되는데, (+)가 왼쪽에 있으면 RIGHT OUTER, 오른쪽에 있으면 LEFT OUTER. ③ USING·NATURAL JOIN의 공통 컬럼엔 테이블명/별칭을 붙이지 않음 .

> \*\*🔎 건수 계산 예\*\* A테이블 4행, B테이블 3행, 공통 2건이면 → INNER 2, LEFT 4, RIGHT 3(공통2+B단독1 형태에 따라), FULL 5, CROSS 4×3=12. 벤다이어그램으로 "어느 쪽을 다 살리나"를 떠올리세요.

### 2. 계층형 쿼리 (Hierarchical Query)

조직도·게시판 댓글처럼 **부모-자식 구조**를 조회합니다 (SELF JOIN 형태).

    SELECT LEVEL, 사원
      FROM 사원테이블
     START WITH 상위사원 IS NULL -- 루트(시작점)
    CONNECT BY PRIOR 사원 = 상위사원;  -- 부모→자식 전개

| 구문                  | 의미                                             |
|-----------------------|--------------------------------------------------|
| `LEVEL`               | 현재 깊이(Depth). 루트=1. 리프가 가장 큰 값      |
| `START WITH`          | 시작(루트) 노드 지정                             |
| `CONNECT BY`          | 부모-자식 연결 규칙. PRIOR 위치로 순/역방향 결정 |
| `SYS_CONNECT_BY_PATH` | 루트부터 현재까지 경로 출력                      |
| `CONNECT_BY_ROOT`     | 최상위 루트 값 표시                              |
| `CONNECT_BY_ISLEAF`   | 최하위(리프)면 1, 아니면 0                       |
| `NOCYCLE`             | 순환(CYCLE) 발생 시 멈춤                         |

> 시험 포인트 ① PRIOR 위치에 따라 순방향/역방향 전개 가능. ② WHERE 는 START WITH…CONNECT BY로 전개가 끝난 뒤 필터링. ③ TRIM 은 계층형 함수가 아님(함정). ④ 동일 레벨 정렬은 ORDER SIBLINGS BY .

### 3. 윈도우 함수 (Window Function)

행을 그룹으로 묶지 않고도 **그룹별 계산·순위**를 각 행 옆에 보여줍니다. `OVER()`가 핵심.

    SELECT 사원, 급여,
           RANK() OVER(PARTITION BY 부서 ORDER BY 급여 DESC) 순위
      FROM 사원;  -- 부서별로 급여 높은 순 순위

#### 순위 함수 (★빈출)

| 함수         | 동점 처리 (1,1 다음)                           |
|--------------|------------------------------------------------|
| `RANK`       | 동점은 같은 순위, 다음은 **건너뜀** (1,1,3)    |
| `DENSE_RANK` | 동점은 같은 순위, 다음은 **안 건너뜀** (1,1,2) |
| `ROW_NUMBER` | 동점도 무조건 순차 (1,2,3)                     |

#### 기타 함수 & 윈도우 범위

| 구문                       | 의미                            |
|----------------------------|---------------------------------|
| `FIRST_VALUE / LAST_VALUE` | 정렬 후 첫 / 마지막 값          |
| `LAG / LEAD`               | 이전 / 다음 행 값               |
| `RATIO_TO_REPORT`          | 파티션 합계 중 비율             |
| `CUME_DIST / PERCENT_RANK` | 누적 백분율 (0~1)               |
| `NTILE(n)`                 | n개 등급으로 분할               |
| `ROWS` / `RANGE`           | 행 자체 기준 / 값 기준          |
| `UNBOUNDED PRECEDING`      | 시작점에만 사용(파티션 첫 행)   |
| `UNBOUNDED FOLLOWING`      | 끝점에만 사용(파티션 마지막 행) |

> 시험 포인트 RANK vs DENSE_RANK 차이(건너뛰기 유무)가 단골. UNBOUNDED PRECEDING은 끝점에 못 옴 . 비율 함수(CUME_DIST·PERCENT_RANK·RATIO_TO_REPORT)는 0~1 범위.

### 4. 연산자 우선순위 · SQL 실행 순서

연산자 우선순위

산술 → 연결(`||`) → 비교 → `IN·LIKE·BETWEEN·IS NULL` → **NOT → AND → OR**

SQL 실행 순서

**FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY**

> 암기팁 실행 순서: " 프 → 웨 → 그 → 하 → 셀 → 오 ". SELECT는 거의 마지막, ORDER BY가 진짜 마지막. 작성 순서와 실행 순서가 다른 점이 함정!

### 5. CASE · DECODE · 기타 자주 나오는 것

| 구문                               | 설명                                                       |
|------------------------------------|------------------------------------------------------------|
| `CASE WHEN 조건 THEN … ELSE … END` | IF-THEN-ELSE 논리. 범위 조건 가능                          |
| `DECODE(컬럼, A, 결과1, 기본값)`   | Oracle 전용. **= 비교만** 가능                             |
| `NULL 비교`                        | 반드시 `IS NULL` / `IS NOT NULL` (CASE로 =NULL 비교 불가!) |
| `ANY / ALL`                        | ANY=하나라도 만족, ALL=모두 만족 (다중행)                  |
| `COUNT(*)` vs `COUNT(컬럼)`        | \*는 NULL 포함 전체, 컬럼은 NULL 제외                      |
| 순수 관계 연산자                   | SELECT, PROJECT, JOIN, DIVIDE                              |

> 시험 포인트 ① CASE COL WHEN NULL THEN… 은 NULL을 못 잡음 → 반드시 IS NULL . ② DISTINCT COL1, COL2 = GROUP BY COL1, COL2 (중복 제거). ③ 정규표현식 ^ =시작, \$ =끝.

**❓ 확인 퀴즈 · 실행 순서**

SQL문의 실행 순서로 올바른 것은?

1.  FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
2.  FROM → WHERE → HAVING → GROUP BY → SELECT → ORDER BY
3.  SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY
4.  FROM → WHERE → GROUP BY → SELECT → HAVING → ORDER BY

> 정답 ① FROM으로 테이블 선택 → WHERE 필터 → GROUP BY/HAVING 그룹 → SELECT 인출 → ORDER BY 정렬.

### 6. GROUP BY · HAVING

데이터를 묶어서 집계(합계·평균·개수 등)할 때 씁니다.

    SELECT 부서, COUNT(*) FROM 사원
     WHERE 급여 > 3000      -- ① 그룹 전 행 필터
    GROUP BY 부서          -- ② 부서별로 묶기
    HAVING COUNT(*) >= 5;   -- ③ 그룹 후 조건

> 시험 포인트 ① WHERE는 그룹 전, HAVING은 그룹 후 필터. ② SELECT에 집계함수와 함께 쓴 일반 컬럼은 반드시 GROUP BY에 들어가야 함. ③ 집계함수(SUM/AVG/COUNT(컬럼))는 NULL 제외, COUNT(\*) 만 NULL 포함.

### 7. 조인 보충 — SELF · NATURAL · ANSI

| 조인             | 설명                                                                                                 |
|------------------|------------------------------------------------------------------------------------------------------|
| **SELF JOIN**    | 한 테이블을 **자기 자신과** 조인 (별칭 2개 사용). 사원-상사 관계 등                                  |
| **NATURAL JOIN** | 두 테이블의 **같은 이름·타입 컬럼**을 자동으로 EQUI JOIN. 공통 컬럼에 테이블명·별칭 **붙이면 안 됨** |
| **USING**        | 공통 컬럼 중 **원하는 것만** 골라 조인. 역시 별칭 금지                                               |
| **ON**           | 조인 조건을 직접 지정 (컬럼명 달라도 가능)                                                           |

> Oracle (+) ↔ ANSI 변환 (+) 가 왼쪽 에 있으면 → RIGHT OUTER JOIN, 오른쪽 에 있으면 → LEFT OUTER JOIN. 기호 반대쪽을 다 살린다고 기억!

### 8. TOP-N 쿼리 (상위 N건 조회)

| 방식             | 문법                                                                |
|------------------|---------------------------------------------------------------------|
| Oracle `ROWNUM`  | `WHERE ROWNUM <= 5` (정렬이 필요하면 **인라인 뷰로 ORDER BY 먼저**) |
| ANSI `FETCH`     | `ORDER BY 급여 DESC FETCH FIRST 5 ROWS ONLY`                        |
| `OFFSET … FETCH` | `OFFSET 10 ROWS FETCH NEXT 5 ROWS ONLY` (11~15위)                   |
| SQL Server `TOP` | `SELECT TOP 5 … `                                                   |

> 함정 주의 WHERE ROWNUM \<= 5 ORDER BY ... 는 정렬 전에 5건을 잘라버려 원하는 상위 5건이 아닐 수 있음. 반드시 정렬된 인라인 뷰를 먼저 만든 뒤 ROWNUM을 걸어야 합니다.

### 9. PIVOT / UNPIVOT

**PIVOT**

행 → 열 로 회전. 세로로 쌓인 데이터를 가로 표(교차표)로 집계. (예: 월별 매출을 '1월·2월·3월' 컬럼으로)

**UNPIVOT**

열 → 행 으로 되돌림. 가로로 펼쳐진 컬럼을 세로 데이터로 변환.

> \*\*💡 쉽게 말하면\*\* 엑셀 '피벗 테이블'과 같은 개념이에요. PIVOT = 세로 목록을 가로 요약표로, UNPIVOT = 그 반대. 방향만 기억하면 됩니다.

### 10. 정규표현식 (Regular Expression)

| 기호/함수       | 의미                            |
|-----------------|---------------------------------|
| `^` / `$`       | 문자열의 **시작** / **끝**      |
| `.`             | 임의의 한 문자                  |
| `*` / `+` / `?` | 앞 문자 0개↑ / 1개↑ / 0~1개     |
| `[ ]` / `[^ ]`  | 안의 문자 중 하나 / 제외한 하나 |
| `|`             | OR                              |
| `REGEXP_LIKE`   | 패턴 일치 여부 (WHERE 조건)     |
| `REGEXP_SUBSTR` | 패턴에 맞는 부분 문자열 추출    |

> 시험 포인트 ^ =시작, \$ =끝이 단골. \[ \] 는 '하나와 일치', \[^ \] 는 '제외'. 자주 나오진 않지만 기호 뜻만 알면 풀립니다.

**❓ 확인 퀴즈 · TOP-N**

정렬된 상위 5건을 올바르게 조회하는 Oracle 방식은?

1.  SELECT \* FROM 사원 WHERE ROWNUM \<= 5 ORDER BY 급여 DESC
2.  SELECT \* FROM (SELECT \* FROM 사원 ORDER BY 급여 DESC) WHERE ROWNUM \<= 5
3.  SELECT TOP 5 \* FROM 사원 ORDER BY 급여 DESC
4.  SELECT \* FROM 사원 LIMIT 5

> 정답 ② ROWNUM은 정렬 전에 적용되므로, 정렬된 인라인 뷰를 먼저 만든 뒤 ROWNUM을 걸어야 진짜 상위 5건이 나옵니다. (TOP은 SQL Server, LIMIT은 MySQL)

> 정답 ④ DROP은 구조·데이터 모두 삭제. CASCADE는 Oracle에만 있고, 참조 제약조건까지 삭제합니다.
